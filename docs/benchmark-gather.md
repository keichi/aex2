# mdx2: gather が省く往復

小さい選択をいくつも取るとき、1 個ずつ取るのと `gather` でまとめて取るのを、
`netem` で往復遅延を 0〜100 ms 足しながら比べた記録である。測定日 2026-09-18。

## 結論

1. **`gather` は N 個の選択を 1 往復で返す。** 1 個ずつなら N 往復かかるので、
   遅延が効く場所では倍率がそのまま N に近づく。往復 100 ms で 64 個なら
   **6,460 ms 対 102 ms (63.5 倍)**、往復 5 ms でも 56.1 倍だった
2. **選択 1 個あたりの固定費は約 8 µs** (往復 0 ms・64 個で 0.49 ms)。
   したがって倍率の上限は「RTT ÷ 8 µs」で決まり、遅延のない同一ホストでは
   64 個でも 14.5 倍で頭打ちになる。逆に言えば、WAN では N を増やすほど効く
3. **測定中に、inline 返却が 1 往復ではなく 2 往復になっている不具合が見つかった** (下記)。
   直したので、`inline_limit_bytes` 以下の選択は設計どおり 1 往復で返る

## 測定が見つけた不具合: 制御プレーンの `TCP_NODELAY`

サーバは自前の listener を tonic に渡しているため、tonic の `tcp_nodelay` が
受け入れたソケットに届いていなかった。1 セグメントを超える応答は最後の断片が
Nagle に握られ、クライアントの ACK を待つ。**inline 返却 (SPEC §5.6.2) は
まさにその 1 往復を削るための経路**なので、その効果が消えていた。

| 往復遅延 | `GetItem` (メタデータのみ) | 4 KiB の inline 読み (修正前) | 同 (修正後) |
|---|---|---|---|
| +1 ms | 1.13 ms | 2.18 ms | 1.13 ms |
| +5 ms | 5.15 ms | 10.22 ms | 5.17 ms |
| +25 ms | — | — | 25.85 ms |
| +100 ms | — | — | 100.91 ms |

修正後は `GetItem` と同じ時間になっており、小さい選択が 1 往復で返ることを確認できる。
SPEC §5 が「ライブラリに listener を自前で渡すときは TCP 設定が適用されない」と
書いていた罠そのものだった。

[eval-mdx2.md](eval-mdx2.md) に従った。

3 パス回し、各パスで全条件を 1 回ずつ測った中央値を載せる。1 パス内の各点は

読み方:

- **`gather` の時間は往復 1 回分 + N × 8 µs** である。往復 100 ms・64 個の 101.72 ms は、
  `GetItem` 1 回 (101.19 ms) に 0.5 ms 足しただけで、選択の数はほとんど効いていない
- **1 個ずつの時間は N × 往復 1 回分**に正確に乗る (往復 100 ms・64 個で 6,460 ms ≒ 64 × 101 ms)
- 倍率が N そのものにならないのは、この固定費と、`gather` 自身の 1 往復のぶんである

## この測定でわかっていないこと

- 1 選択 4 KiB しか測っていない。`inline_limit_bytes` を超える選択が混ざると、
  `gather` はデータプレーンへ 1 つのキューとして流す経路になり、性質が変わる
- 64 個までしか測っていない。Python 側は `max_transfers_per_session` (既定 64) ごとに
  分けて送るので、それ以上はこの倍率が段階的に頭打ちになるはずである
