# Linux での転送性能

SPEC が最適化対象としているのは Linux である。これまでの測定はすべて macOS
(Apple M4) で行っていたので、Linux 機で測り直した記録である。測定日 2026-09-16。

**結論を先に書くと、3 つある。**

1. **機械の性格がまったく違う。** macOS 機ではメモリ帯域が余っていてループバックが
   速かった。Linux 機ではその逆で、**ソケットが律速**する。実ネットワークに近いのは
   こちらである
2. **ダブルバッファリングは Linux でも効く** (+57 %)。しかも**ストレージを読む費用が
   完全に消える** — 合成バックエンドとの差がなくなる
3. **ただしスレッド配置に支配される。** 読みスレッドと送りスレッドが別の L3 に乗ると
   27 % 落ち、放っておくと全体で 36 % 落ちる。**これは直すべきである**

## 測定環境

| 項目 | Linux 機 | 比較: macOS 機 |
|---|---|---|
| ホスト | AMD Ryzen 9 5900X (12 コア、SMT 無効) | Apple M4 (4P + 6E) |
| L3 | 32 MiB × 2 (**CCD が 2 つ、L3 は共有されない**) | 共有 |
| メモリ | 62 GiB DDR4 | 32 GiB LPDDR5X |
| OS | Ubuntu 22.04.5 (kernel 6.8.0) | macOS 26.6.2 |
| ストレージ | WD Black SN750 NVMe (`/`) | Apple Fabric NVMe |
| メモリ常駐 | tmpfs (`/dev/shm`) | RAM ディスク (HFS+) |
| Rust | 1.98.1、`--release` | 同じ |
| iPerf3 | 3.17.1 | 3.21 |

コールドキャッシュは **`posix_fadvise(POSIX_FADV_DONTNEED)`** で作る (`dropcache`)。
root が要らず、macOS でやっていた「RAM より大きいファイルの後半を読む」方式より
はるかに正確で、**繰り返しのばらつきが ±0.5 % に収まる** (macOS では ±15 %)。

テストは Linux でも全通過する (199 件)。clippy も警告なし。

## 基準値 — 律速がどちらにあるか

| | Linux (5900X) | macOS (M4) |
|---|---:|---:|
| `memcpy` の上限 | 14,080 MiB/s | 47,000 MiB/s |
| iPerf3 ループバック、1 ストリーム | 5,204 MiB/s | 19,501 MiB/s |
| iPerf3 ループバック、4 ストリーム | 16,410 MiB/s | — |
| `pread` メモリ常駐 | 11,583 MiB/s (tmpfs) | 17,000〜20,477 MiB/s |
| `pread` NVMe コールド | 2,870 MiB/s | 約 3,100 MiB/s |

**macOS 機では `memcpy` (47,000) がループバック (19,501) の 2.4 倍で、メモリに余裕が
あった。Linux 機では逆に、ループバック (5,204) が `memcpy` (14,080) の 1/2.7 で、
ソケットが最も遅い。** 実ネットワークではリンクが最も遅いので、**Linux 機のほうが
実運用に近い比率**である。

### この 2 つの数字は妥当か

どちらも確かめた。

**`memcpy` 14,080 MiB/s は、このマシンのメモリの限界である。** 読み・書き・コピーを
並べて測ると、

| スレッド数 | 読み | 書き | コピー |
|---:|---:|---:|---:|
| 1 | 22,734 MiB/s | 13,020 | 11,990 |
| 2 | 29,123 | 13,821 | 13,517 |
| **4** | **30,258** | 13,735 | **13,990** |
| 8 | 29,480 | 13,219 | 13,719 |

読みは 30,258 MiB/s (31.7 GB/s) で頭打ちになる。**コピーは 1 バイトあたりメモリを
2 バイト動かす**ので、上限は読みの半分の 15,129 MiB/s。実測 13,990 はその **92 %** で
あり、遅いのではなく限界に張り付いている。

ついでに分かること: 読みの 31.7 GB/s をデュアルチャネル DDR4 の理論値と突き合わせる
と、8 バイト × 2 チャネル × 約 2.0 GT/s になる。読み専有で理論値の 9 割前後は出るので、
**このマシンのメモリは DDR4-2133 (JEDEC 既定) で動いている可能性が高い**。DDR4-3200
なら理論 51.2 GB/s で読みは 44 GB/s 前後になるはずである。BIOS で XMP / DOCP が有効に
なっていないのではないか。`sudo dmidecode -t memory | grep -i speed` で確認できる。
有効にすれば、**ここに書いたすべての数字が 5 割ほど上がる**見込みである。

**iPerf3 が `memcpy` の 1/2.7 なのは、メモリではなく CPU で詰まっているからである。**
iPerf3 自身が報告する CPU 使用率は

```
CPU Utilization: local/sender 101.0% (0.2%u/100.9%s), remote/receiver 68.8%
```

**送信側は 1 コアを使い切っていて、そのほぼ全部がカーネル内 (system) である。**
`perf stat` でも 1.018 CPUs utilized、IPC 0.52、時間の 99.9 % が sys だった。

1 コアあたりで比べると、

| 1 コアがやること | スループット | バイトあたりサイクル |
|---|---:|---:|
| `memcpy` | 11,990 MiB/s | 0.39 |
| ループバック TCP の送信 | 5,204 MiB/s | 0.90 |

**カーネルの送信経路は `memcpy` の 2.3 倍のサイクルを食う。** 内訳はユーザ空間との
コピー (非一時ストアが使えないので所有権取得の分が余計にかかる)、64 KiB ごとの
`sk_buff` の確保と解放、TCP の状態管理、ソフト IRQ と受信側の起床である。

ストリームを増やすと 1 本 5,204 → 4 本 16,410 MiB/s とほぼ線形に伸びることも、
**メモリ帯域ではなくスレッドあたりの CPU が律速**であることを裏づける (メモリが
律速ならストリームを増やしても伸びない)。バッファは両側とも 1 MiB を使い回すので、
データはおおむね L3 に収まり、DRAM をほとんど触らない。

これは AEX2 の挙動とも整合する。サーバの送りスレッドが同じカーネル経路を通る以上、
**1 スレッドでは頭打ちになる** — だから読みを別スレッドに分けるだけで 57 % 伸び、
2 スレッドが別の L3 に乗ると 27 % 落ちるのである。

## AEX2 の結果

4 GiB を 1 転送、チャンク 16 MiB、n = 9。サーバをコア 0-2、クライアントをコア 3-5 に
固定 (どちらも同じ L3)。

| | 逐次 | ダブルバッファリング | 効果 |
|---|---:|---:|---:|
| **`.npy` on tmpfs** | 4,268 MiB/s | **6,694 MiB/s** | **+57 %** |
| 合成バックエンド (ストレージ無し) | 6,400 MiB/s | 6,455 MiB/s | +0.9 % |
| `.npy` on NVMe コールド | 1,844 MiB/s | 2,183 MiB/s | +18 % |

### ストレージを読む費用が消える

macOS では、ストレージを経路から外すと 18 % 速くなった。**Linux では 0.9 % しか
変わらない** (6,694 → 6,455、誤差の範囲で同じ)。

理由は基準値どおりである。tmpfs からの `pread` は 11,583 MiB/s で、ソケットの
5,204 MiB/s より 2 倍以上速い。**遅いほうと重ねてしまえば、速いほうの費用は消える。**
これがダブルバッファリングの本来の効き方であり、SPEC §6.5.3 が狙っていたものである。

逐次のままだと読みは足し算で効くので、4,268 (`.npy`) と 6,400 (合成) の 50 % の差に
なる。**重ねた瞬間にその差が 0.9 % になる。**

### コールドディスク

| | スループット |
|---|---:|
| 逐次 | 1,840 / 1,850 / 1,841 MiB/s |
| ダブルバッファリング | 2,191 / 2,177 / 2,180 MiB/s |
| `pread` の上限 | 2,870 MiB/s |

**+18 %、しかも ±0.5 %。** macOS では誤差に埋もれて判定できなかったが、Linux では
明確に効いている。`posix_fadvise` による退避が正確なおかげで見える。

## スレッド配置が 36 % を持っていく

Ryzen 9 5900X は 12 コアが **2 つの CCD に分かれ、L3 が別々**である (コア 0-5 と 6-11)。
読みスレッドが埋めたバッファを送りスレッドが読むので、2 つが別の CCD にいると
**バッファが毎回 Infinity Fabric を渡る**。

読みスレッドと送りスレッドだけをコアに固定して比べると、

| サーバの 2 スレッドの置き場所 | スループット (3 回) |
|---|---:|
| コア 0,1 (**同じ L3**) | 3,427 / 3,607 / 3,755 MiB/s |
| コア 0,6 (**別の L3**) | 2,819 / 2,895 / 2,832 MiB/s |

**同じ L3 なら +27 %、3 回中 3 回。**

固定をやめて Linux のスケジューラに任せると、こうなる。

| | 逐次 | ダブルバッファリング |
|---|---:|---:|
| 同じ L3 に固定 | 4,268 MiB/s | **6,694 MiB/s** |
| 固定なし (現状の出荷形) | 3,839 MiB/s | 4,290 MiB/s |
| 差 | −10 % | **−36 %** |

しかも固定なしのダブルバッファリングは**測定ごとに 3,268〜6,717 MiB/s と 2 倍振れる**。
スケジューラがたまたま近くに置けば速く、離せば遅い。CPU も 0.18 → 0.25 s/GiB に増える。

つまり、**いまの実装は chiplet CPU 上で「当たれば速い」状態**である。macOS 機は
P コアが L3 を共有しているのでこの問題が出ず、気づけなかった。

### 直し方

接続ごとの読みスレッドと送りスレッドを**同じ L3 ドメインに固定する**。Linux では
`sched_setaffinity` で、`/sys/devices/system/cpu/cpu*/cache/index3/shared_cpu_list`
から L3 の割り当てを読めばよい。接続 N 本を L3 ドメインへ順に配る形になる。

未実装である。設計判断を含むので、[M4 に向けて](#m4-に向けて) に回す。

## `sendfile` — macOS と逆の結論

[macOS では負けた](sendfile.md)。Linux では**メモリ常駐データで勝つ**。

同じ受信側へ 4 GiB、コア 0-5 に固定。

| データ | 断片 | 逐次 | 重ねる (現行) | `sendfile` |
|---|---:|---:|---:|---:|
| tmpfs | 512 KiB | 3,904 | 6,088 | **7,360** |
| tmpfs | 4 MiB | 3,297 | 3,537 | **5,582** |
| NVMe コールド | 4 MiB | 1,968 | **2,811** | 2,357 |

CPU は tmpfs 512 KiB で、逐次 0.40 / 重ねる 0.39 / **`sendfile` 0.26 s/GiB**。

- **メモリ常駐では `sendfile` が 21〜58 % 速く、CPU は 33 % 少ない。** Linux の
  `sendfile` は splice 機構でページを参照で渡せるため、コピーが本当に減る。macOS の
  実装にはそれがない
- **コールドディスクでは負ける** (2,357 対 2,811)。`sendfile` は 1 本のスレッドが
  1 度に 1 つのことをするので、**ディスクの読みと送りを重ねられない**。重ねられる
  現行方式のほうが速い

### それでも採らない理由は変わらない

1. **効く範囲が狭い。** 非圧縮・無加工の転送にしか使えない。Zarr / HDF5 は圧縮チャンク
   が前提で、適応品質を入れた時点で加工経路が主になる。**`.npy` にしか効かず将来消える**
2. **コールドディスクでは負ける。** 本基盤が想定するのは RAM に収まらないデータである
3. **恒久的な複雑さ。** OS ごとに引数の意味すら違う (macOS はヘッダ長を送信長に含め、
   Linux はヘッダを運べない)

**再検討に値するのは「メモリ常駐データを配る用途で、CPU が律速するとき」**である。
そのときは `sendfile` + 別スレッドの `posix_fadvise(WILLNEED)` で先読みすれば、
コピー削減と重なりの両方が取れる可能性がある。SPEC §7.1 の `zero_copy_source()` を
足せば、フレームプロトコルもトレイトも変えずに載る。

## 実ネットワークではどうなるか

**10 GbE は 1,192 MiB/s である。上の表のどの数字もそれを上回っている** — コールド
ディスクの 2,183 MiB/s ですら 1.8 倍。したがって 10 GbE の LAN では、ここで見えている
差はすべてリンクに吸収されて消え、残るのは CPU 使用率だけになる。

差が意味を持つのは 100 GbE 級 (11,920 MiB/s) であり、そこでは
**スレッド配置の 36 % が効いてくる**。

## macOS との対比

| | macOS (M4) | Linux (5900X) |
|---|---:|---:|
| メモリ常駐、逐次 | 7,966 MiB/s | 4,268 MiB/s |
| メモリ常駐、ダブルバッファリング | 12,048 MiB/s | 6,694 MiB/s |
| ダブルバッファリングの効果 | +51 % | +57 % (配置次第で +12 %) |
| ストレージを外すと | +18 % | +0.9 % |
| コールドディスクでの効果 | +3 % (誤差内) | +18 % (±0.5 %) |
| `sendfile` | 負ける | メモリ常駐は勝ち、ディスクは負け |
| 律速 | メモリ帯域 | ソケット (スレッドあたり CPU) |

**ダブルバッファリングは両方で効く**という点は揺らがない。効き方の説明が違うだけで、
どちらも「遅いほうと重ねれば速いほうは消える」という同じ理屈である。

## M4 に向けて

Linux での測定から、優先順位はこうなる。

1. **読みスレッドと送りスレッドを同じ L3 に固定する。** 単一接続で 36 %。並列接続に
   すると接続ごとに 2 スレッド増えるので、放置すると悪化する見込みが高い
2. **複数接続。** iPerf3 が 1 → 4 ストリームで 5,204 → 16,410 MiB/s になることから、
   このマシンにはまだ 3 倍の余地がある
3. credit パイプライン。チャンク 16 MiB が 4 MiB より速いままなので、往復ぶんは残って
   いる

## 再現方法

Linux 機には Rust 1.98.1 のほか、`protoc` 3.15 以降 (Ubuntu 22.04 の 3.12 は proto3
optional を扱えない) と `iperf3` が要る。どちらも root なしで `~/.local` に入る。

```console
$ cargo build --release
$ mkdir -p /dev/shm/aex && target/release/mknpy /dev/shm/aex/mem.npy 1073741824
$ taskset -c 0-2 target/release/aex-server --config aex.toml &
$ taskset -c 3-5 target/release/aexbench http://127.0.0.1:50191 mem.npy \
      --bytes $((4<<30)) --chunk $((16<<20)) --reps 9

$ target/release/dropcache /path/to/disk.npy     # コールドキャッシュを作る
$ target/release/memcpybench                      # メモリコピーの上限
```
