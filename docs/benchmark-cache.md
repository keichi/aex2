# mdx2: クライアント側キャッシュ

[クライアント側キャッシュ](../SPEC.md) (SPEC §10.7) は、取得済みの結果に含まれる要求を
往復せずに手元で切り出す。対話的な使い方 (広く取ってから一部を何度も見る) で
どれだけ効くか、外れたときに何を払うかを、遅延を足した VM 間で測った。

測定日 2026-11-05。

## 結論

1. **ヒットは遅延に依らず 0.04 〜 0.1 ms** (スライスの要求)。回線に出ないので当然だが、
   実測でもそうなった。追加 RTT 100 ms では転送の **1,007 〜 10,897 倍**速い
2. **fancy index の要求はヒットでも数 ms かかる。** numpy がコピーで結果を作るため、
   ランダムな 1,024 行 (8 MiB) で 3.1 ms、10 万点で 6.5 ms。それでも 100 ms では
   113 〜 232 倍速い。追加 RTT 0 では 1,024 行が 2.0 倍にとどまる
3. **埋めるコストは数回で取り返す。** 64 MiB の領域を埋めるのに 100 ms で 2.8 秒。
   4 MiB のタイルを 4 回読めば元が取れる
4. **外れたときの上乗せは、この回線の揺れより小さくて測れなかった。** 判定だけして
   格納しないクライアントと、キャッシュの無いクライアントの差は符号が揃わない。
   上限はヒットの時間から言える (判定 + 切り出しがヒット、判定だけがミス): スライスで
   0.1 ms 以下、10 万点で 6.5 ms 以下

## 条件

環境は [mdx2 の測定](benchmark-mdx2.md#測定環境) と同じ。手順は
[eval-mdx2.md](eval-mdx2.md) に従った。

| | 値 |
|---|---|
| サーバ / クライアント | `aex2-eval-1` / `aex2-eval-2` |
| REVISION | `1863103` (両方) |
| AEX2 サーバ | `benchmarks/mdx2/aex.toml` (制御 50191) |
| ファイル | `/mnt/aexram/wave.npy` (131072 × 2048、float32、1 GiB) |
| 読み手 | `benchmarks/mdx2/cachebench.py` (掃引は `cache-sweep.sh 5 20`) |
| 追加 RTT | netem で 0 / 5 / 25 / 100 ms |
| sysctl | 既定のまま (`tcp_rmem` / `tcp_wmem` の上限 6 / 4 MiB) |
| iPerf3 (サーバ→クライアント) | 前 22.4 / 149 Gbit/s、後 24.2 / 183 Gbit/s (1 本 / 16 本) |

- 3 つのクライアントが同じ要求を順に読む。**hit** は `cache_bytes=1 GiB` で、先に
  `wave[0:8192, :]` (64 MiB) を取ってある。**transfer** はキャッシュ無し。**probe** は
  `cache_bytes=1` で、毎回判定して走査するが何も格納しない
- 要求はすべてその 64 MiB の内側にある。1 回ごとに要求を変え、3 つは同じ要求を交互に読む
- 各点 20 回の中央値を 1 周とし、遅延を一巡する周を 5 回回して、その中央値を採った (n = 5)
- 各回の最初に結果が 3 つで一致すること、最後に hit が埋めた後 1 バイトも送っていない
  ことを assert している
- 16 本の iPerf3 は前後で 23 % 動いた (手順書の目安は 10 %)。ただし要求は最大 8 MiB で、
  帯域ではなく RTT で決まる測定なので、測り直していない

## 結果

単位は ms。

| 要求 | 大きさ | ヒット 0 | 5 | 25 | 100 |
|---|---:|---:|---:|---:|---:|
| 1 行の先頭 (`[i, 0:1024]`) | 4 KiB | 0.084 | 0.081 | 0.088 | 0.101 |
| 512 行のタイル | 4 MiB | 0.040 | 0.041 | 0.074 | 0.074 |
| 8 刻みの間引き (`[::8, ::8]`) | 1 MiB | 0.036 | 0.051 | 0.086 | 0.095 |
| ランダムな 1,024 行 | 8 MiB | 3.11 | 3.11 | 3.36 | 3.48 |
| 10 万点 (軸ごとのインデックス配列) | 0.38 MiB | 6.55 | 6.49 | 6.72 | 6.75 |

| 要求 | 転送 0 | 5 | 25 | 100 | 倍率 0 | 5 | 25 | 100 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 行の先頭 | 0.852 | 5.88 | 26.2 | 101 | 10 | 73 | 297 | 1,007 |
| 512 行のタイル | 3.06 | 17.5 | 221 | 809 | 76 | 429 | 3,006 | 10,897 |
| 8 刻みの間引き | 3.56 | 14.2 | 92.4 | 807 | 99 | 276 | 1,073 | 8,474 |
| ランダムな 1,024 行 | 6.29 | 29.0 | 157 | 809 | 2 | 9 | 47 | 232 |
| 10 万点 | 73.5 | 86.7 | 235 | 764 | 11 | 13 | 35 | 113 |

領域を埋める転送 (64 MiB) は 49.5 / 178 / 806 / 2,825 ms だった。

- **ヒットの時間は追加 RTT に関係しない。** 0 と 100 ms の差は最大 0.06 ms で、
  これは回線ではなく Python 側の揺れである
- **スライスの要求は view を返すだけ**なので、4 MiB でも 4 KiB より速い。4 KiB の行が
  遅いのは中身ではなく、判定にかかる固定の時間 (`_aex.resolve` を含む) が見えているため
- **fancy index の要求は、ヒットの時間の大半が numpy のコピー**である。10 万点の 6.5 ms
  には、インデックスを Rust で正規化して戻す往復と、`divmod` による判定も入っている
- 転送側では、+100 ms で 1 〜 8 MiB の要求がどれも約 8 RTT かかっている。キャッシュとは
  別の問題として調べている

### 外れたときの上乗せ

probe と transfer の差 (ms)。

| 要求 | 0 | 5 | 25 | 100 |
|---|---:|---:|---:|---:|
| 1 行の先頭 | −0.57 | −0.26 | −0.15 | −0.12 |
| 512 行のタイル | −0.23 | +0.11 | +10.9 | +1.90 |
| 8 刻みの間引き | −0.46 | −0.37 | +12.7 | −502 |
| ランダムな 1,024 行 | +0.08 | −0.40 | +1.00 | +0.70 |
| 10 万点 | −9.08 | −12.0 | −7.77 | −6.77 |

**符号が揃わないので、この表から上乗せは読めない。** 判定を足したほうが 500 ms 速い
という点まであり、これはクライアントごとに別の TCP 接続を持ち、輻輳ウィンドウの状態が
違うことによる揺れと見ている。上乗せの上限はヒットの時間で押さえられる (結論 4)。

## 再現方法

[eval-mdx2.md](eval-mdx2.md) の手順 1 〜 4 のあと、`/mnt/aexram/wave.npy` を作る:

```console
$ ssh aex2-eval1 'cd aex2 && target/release/mknpy /mnt/aexram/wave.npy 268435456 --row-elements 2048 --field wave'
$ ssh aex2-eval2 "tmux new-session -d -s sweep 'cd aex2 &&
    SERVER=192.168.100.207 CLIENT=192.168.101.235 \
    bash benchmarks/mdx2/cache-sweep.sh 5 20 2>&1 | tee ~/cache-sweep.txt'"
```

1 点だけなら:

```console
$ ssh aex2-eval2 "bash -lc 'cd aex2 && .venv/bin/python benchmarks/mdx2/cachebench.py \
    192.168.100.207:50191 wave.npy --reps 20'"
```
