# mdx2: zarr-python にも同じ回線を渡らせた比較

[Zarr の測定](benchmark-zarr.md) の zarr-python 比較は非対称だった。zarr-python は
ストアを持つマシンの上でローカル読みし、AEX2 だけが VM 間のリンクを渡っていた。
査読で必ず来る「Zarr を S3/HTTP に置いて fsspec で読めば済むのでは」に答えるには、
**両方がネットワークを渡る形**で測り直す必要がある。

そこで `/mnt/aexram` を nginx でも配り、同じストア・同じリンク・同じ言語
(どちらも Python) で読み比べた。測定日 2026-09-21。

後半は続きで、**生バイト以外を送った場合** ── 可逆の deflate と誤差保証圧縮 SZ3 ──
を測った (2026-09-22)。前半で唯一 zarr-python が勝った場面に対する答えになるかを
確かめるためである。

## 結論

1. **HTTP に置いても zarr-python はほとんど落ちない。** ローカル読みに対して
   1 プロセスで 0 〜 16 %、16 プロセスで 16 〜 27 % 減るだけである。**相手は強い** ──
   nginx は伸長をしないので送るだけの仕事で済み、伸長はクライアントの 16 コアが払う
2. **同じ土俵に乗せても AEX2 が速い。** マシン全体を使わせた zarr-python (16 プロセス)
   に対して Python クライアントで **1.53 〜 2.01 倍**、Rust の `aexbench` で
   **1.94 〜 2.51 倍**。非対称だった前回の比較 (1.54 〜 2.17 倍) とほぼ同じ値であり、
   **あの数字はネットワークを渡っていたから出ていたのではなかった**
3. **速さの出どころは「どのマシンのコアで払うか」である。** 1 コアあたりの処理量は
   AEX2 572、zarr-python 362 〜 520 MiB/s で桁は同じ。圧縮の効かないストアでは
   1 GiB あたりの CPU 合計も 2.42 対 2.87 秒とほぼ並ぶ。違うのは、**zarr-python は
   それを全部クライアントの 16 コアで払い、AEX2 はサーバの 16 コアに払わせて
   クライアントを空けておける**ことである
4. **ワイヤに載る量は逆に AEX2 が 3 倍から 33 倍多い。** AEX2 は伸長してから
   生バイトを送るので常に 4 GiB。HTTP は圧縮チャンクのまま送るので
   1,350 MiB (圧縮率 35 %) や 123 MiB (3 %) で済む。**これが遠距離で効く**
5. **よく圧縮できるストアは、遠くなると zarr-python が勝つ。** `mem.zarr` (3 %) では
   追加 RTT 25 ms で逆転し (0.89 倍)、100 ms では 0.79 倍になる。33 分の 1 の
   バイト数が、伸長を肩代わりする利点を上回る。**圧縮の効かない `mem-noisy.zarr`
   (35 %) では全区間で AEX2 が 1.27 〜 1.72 倍**
6. **相手の設定を掃かなければ、この比較は成立しなかった。** zarr-python の
   `async.concurrency` は既定が 10 で、追加 RTT 100 ms ではそれだと 330 MiB/s まで落ちる。
   64 にすると 1,217 MiB/s ── **既定のまま測れば 3.7 倍不当に遅く見せていた**
7. **shard を読むと zarr-python は落ちる** (7,920 → 6,124、4,480 → 3,884)。AEX2 は
   落ちない。取り分がいちばん大きいのは shard のとき (2.01 / 1.97 倍)
8. **回線が細ければ誤差保証圧縮 (SZ3) が答えになる。** 1 Gbit/s では zarr-python の
   **7.0 倍** (誤差上限 1e-3、ワイヤ 1,024 → 118 MiB)、上限 1.0 なら 15.1 倍。
   上限は実測でそのとおり守られる。分岐点はこの場で 10 Gbit/s あたりで、
   それより太ければ誤差を売る意味は無い
9. **相手にも精度を落とさせても 4.5 倍。** `numcodecs.Quantize` を掛けたストアを
   zarr-python に読ませると 1 Gbit/s で 187 MiB/s。AEX2 は**より細かい精度で** 851。
   同じくらいの誤差で `Quantize` + zstd が 1.70 倍、SZ3 は 8.7 倍縮むためで、
   しかも **AEX2 側のストアは無損失のまま**である
10. **圧縮が効くのは「帯域が律速のとき」だけ。** credit は論理バイトで数えるので、
    圧縮しても**往復の回数は減らない**。太い回線では遅延を足しても効かず
    (`mem.zarr`、100 ms で deflate 1,406 対 生バイト 1,693)、近ければ全部損である
    (RTT 0 で 5,630 対 988)。**前半の逆転を消すのは圧縮ではなく in-flight である**
11. **deflate はいちばん高くていちばん縮まない** (実データ的な場で 1.09 倍、
    サーバ CPU 24 s/GiB)。浮動小数点の場に汎用の可逆圧縮を掛ける意味は薄い

## 条件

環境は [mdx2 の測定](benchmark-mdx2.md#測定環境) と同じ。手順は
[eval-mdx2.md](eval-mdx2.md) に従った。

| | 値 |
|---|---|
| サーバ / クライアント | `aex2-eval-1` / `aex2-eval-2` |
| REVISION | `2c07f51` (両方) |
| AEX2 サーバ | `benchmarks/mdx2/aex-decode-cache-64m.toml` (制御 50391) |
| HTTP サーバ | `benchmarks/mdx2/nginx-zarr.conf` (8080、`/mnt/aexram` を配る) |
| ストア | `mem{,-shard,-noisy,-noisy-shard}.zarr` (4 GiB、4 MiB チャンク、zstd) |
| 読み手 | `benchmarks/mdx2/zarr-procs.py` (両方) と `aexbench --prefault` |
| Rust / iPerf3 / kernel | 1.98.1 / 3.16 / 6.8.0-136 |
| zarr-python / numcodecs | 3.4.0 / 0.17.0 |
| fsspec / aiohttp / obstore / nginx | 2026.9.0 / 3.14.3 / 0.11.1 / 1.24.0 |
| sysctl | 掃引の間ずっと `tuned` (`tcp_rmem` / `tcp_wmem` の上限 256 MiB) |
| iPerf3 (サーバ→クライアント) | 前 26.1 / 162、後 26.0 〜 28.8 / 167 Gbit/s (1 本 / 16 本) |

- **両方を同じスクリプトの中で回した。** `zarr-procs.py` が `zarr.open_array(...)[:]` と
  `aex.Client(...).open(...)["array"][:]` を同じループ・同じ計時・同じ確保の仕方で
  読む。どちらも毎回新しい配列を確保する (`aexbench` だけが `--prefault`)
- **条件は 1 回ずつ交互に**回し、中央値を採った (RTT 0 の表は n = 5、掃引は n = 3)
- zarr-python の窓口は **obstore** (`zarr.storage.ObjectStore`)。fsspec + aiohttp より
  速かったため (1 GiB で 1,590 対 1,043 MiB/s)。相手には速いほうを使わせる
- デコードキャッシュは 64 MiB なので、AEX2 は**毎回ほぼ全チャンクを伸長する**
- 4 通りのストアについて、両方の読み手が**同じバイトを返すことを確かめてから**測った
  (`zarr-procs.py --check`)

### nginx が律速でないことの確認

ストアの全チャンク (1,024 ファイル、1.4 GB) を 16 プロセスの `curl` で取ると
**0.087 秒 = 128 Gbit/s** で、iPerf3 の 16 本 (162 Gbit/s) の 79 % に届く。
zarr-python が実際に引く量 (1,500 MiB/s 前後) の 10 倍あるので、
**下の数字は nginx ではなく読み手を測っている**。

`curl -Z` は 1 スレッドなので、1 プロセスだと 24 Gbit/s で頭打ちになる。
この確認は 16 プロセスに分けて行うこと。

## 同じ距離 (VM 間、RTT 0.7 ms)

n = 5 の中央値、MiB/s。zarr-python の「1 プロセス」は `async.concurrency` を
10 / 64 / 256 で掃いた最良値 (括弧内)。

| ストア | zarr 1 プロセス | zarr 16 プロセス | AEX2 1 接続 | AEX2 16 接続 | 対 16 プロセス | `aexbench` 16 |
|---|---:|---:|---:|---:|---:|---:|
| `mem.zarr` | 2,123 (c10) | 7,920 | 1,363 | 12,141 | **1.53 倍** | 15,350 |
| `mem-shard.zarr` | 1,344 (c256) | 6,124 | 1,551 | 12,301 | **2.01 倍** | 15,352 |
| `mem-noisy.zarr` | 1,899 (c10) | 4,480 | 694 | 7,903 | **1.76 倍** | 8,818 |
| `mem-noisy-shard.zarr` | 1,182 (c64) | 3,884 | 753 | 7,659 | **1.97 倍** | 8,527 |

前回の非対称な比較 (zarr-python はローカル読み) では 1.54 〜 2.17 倍だった。
**リモートにしても同じ値が出る** ── あの差はネットワークの有無から来ていたのではない。

zarr-python 自身の落ち幅はローカル読み比で次のとおり。1 プロセスの `mem-noisy.zarr` は
**ローカルとリモートで差が無い** (1,908 → 1,899)。ただし**前回の値は別のセッション**で
取ったもので、zarr-python は回ごとに 10 〜 20 % 振れる。**落ちていないことは言えるが、
落ち幅の数字そのものは信用しないこと**。

| | ローカル (前回) | HTTP 越し | 落ち幅 |
|---|---:|---:|---:|
| 1 プロセス `mem.zarr` | 2,528 | 2,123 | −16 % |
| 1 プロセス `mem-noisy.zarr` | 1,908 | 1,899 | −0.5 % |
| 16 プロセス `mem.zarr` | 10,901 | 7,920 | −27 % |
| 16 プロセス `mem-noisy.zarr` | 5,314 | 4,480 | −16 % |

**1 接続対 1 プロセスは比較の単位として合っていない。** AEX2 の 1 接続は 1 コアで、
credit 16 × 4 MiB = 64 MiB しか飛ばさない。zarr-python の 1 プロセスは 3 コア強を使い、
`concurrency` の数だけ要求を並べる。それでも shard では AEX2 の 1 接続が勝つ
(1,551 対 1,344) ── あちらは shard を読むと partial read を諦めるためである。

## 何をどこで払っているか

同じ転送 (4 GiB) についての、ワイヤのバイト数とサーバ・クライアント双方の CPU。
サーバ側は `/proc/net/dev` と `/proc/<pid>/stat` の差分 (AEX2 サーバと nginx の両方を含む)。

| ストア / 読み手 | ワイヤ | サーバ CPU | クライアント CPU | 合計 CPU |
|---|---:|---:|---:|---:|
| `mem-noisy.zarr` zarr 16 プロセス | 1,350 MiB | 0.17 s | 11.3 s | 2.87 s/GiB |
| `mem-noisy.zarr` AEX2 16 接続 | 4,102 MiB | 7.15 s | 2.5 s | **2.42 s/GiB** |
| `mem.zarr` zarr 16 プロセス | 123 MiB | 0.06 s | 5.0 s | 1.26 s/GiB |
| `mem.zarr` AEX2 16 接続 | 4,101 MiB | 3.95 s | 2.8 s | 1.69 s/GiB |

1 コアあたりの処理量にすると次のようになる (`mem-noisy.zarr`)。

| | MiB/s | CPU s/GiB | 1 コアあたり MiB/s | 使っているコア数 |
|---|---:|---:|---:|---:|
| AEX2 16 接続 (サーバ側) | 7,903 | 1.79 | **572** | 13.8 |
| zarr-python 16 プロセス (クライアント側) | 4,480 | 2.83 | 362 | 12.4 |
| zarr-python 1 プロセス (クライアント側) | 1,899 | 1.97 | 520 | 3.7 |

**伸長そのものの速さで勝っているのではない。** 1 プロセスの zarr-python は
1 コアあたり 520 MiB/s で、AEX2 の 572 と大きくは違わない (16 プロセスで 362 に
落ちるのは、16 個のインタプリタが同じ 16 コアを奪い合うため)。違うのは
**払う場所**である。zarr-python は伸長をクライアントでやるので、利用者の計算ノードの
コアが 1 GiB あたり 2.8 秒持っていかれる。AEX2 はそれをサーバに置き、クライアントには
0.6 秒しか残さない。

その代償が**ワイヤのバイト数**である。AEX2 は常に 4 GiB を送る。ここが次の節につながる。

## 遠くなるとどうなるか

netem で往復を足した掃引。n = 3 の中央値、`zarr-procs.py` の 16 プロセス対
AEX2 の 16 接続 (どちらも Python)。zarr-python の 1 プロセスは掃いた最良値。

### 圧縮が効かないストア (`mem-noisy.zarr`、35 %)

| 追加 RTT | zarr 16 プロセス | AEX2 16 接続 | 比 | zarr 1 プロセス | AEX2 1 接続 |
|---:|---:|---:|---:|---:|---:|
| 0 ms | 4,570 | 7,873 | **1.72** | 1,904 | 675 |
| 5 ms | 4,273 | 6,134 | **1.44** | 2,042 | 713 |
| 25 ms | 3,054 | 3,892 | **1.27** | 1,720 | 594 |
| 100 ms | 1,004 | 1,606 | **1.60** | 1,217 | 451 |

### よく圧縮できるストア (`mem.zarr`、3 %)

| 追加 RTT | zarr 16 プロセス | AEX2 16 接続 | 比 | zarr 1 プロセス | AEX2 1 接続 |
|---:|---:|---:|---:|---:|---:|
| 0 ms | 8,122 | 11,555 | **1.42** | 2,049 | 1,557 |
| 5 ms | 7,583 | 9,074 | **1.20** | 2,086 | 1,446 |
| 25 ms | 5,594 | 4,977 | **0.89** | 1,874 | 1,022 |
| 100 ms | 2,126 | 1,690 | **0.79** | 1,428 | 471 |

**逆転は 5 〜 25 ms の間にある。** 理由は単純で、そこから先はリンクが律速になり、
33 分の 1 のバイト数しか送らない側が勝つ。100 ms で AEX2 が 1,690 MiB/s ということは
ワイヤ上は 14.2 Gbit/s であり、同じ時間に zarr-python は 123 MiB しか送っていない。

圧縮が効かないストアでこれが起きないのは、送る量の比が 3 倍しかないからである。
そこでは伸長を肩代わりする利点が残り、100 ms でも 1.60 倍を保つ。

**AEX2 は既定でストレージ側の圧縮を解いてから生バイトを送る。**
[遠距離で伸長の代金が消える](benchmark-zarr.md#遠くなると伸長の代金は消える)ことの
裏返しとして、**遠くてよく圧縮できるデータでは送る量そのものが効いてくる**。

ただし生バイトしか送れないわけではない。プロトコルには可逆の deflate (`codec="gzip"`) と
誤差保証圧縮 (SZ3 / ZFP) があり、**転送ごとに**選べる。それで上の逆転が消えるのか、
何と引き換えなのかは [次の節](#生バイトの代わりに何を送るか) で測った。

### 相手の設定を掃くことの重み

`mem-noisy.zarr`、1 プロセスの `async.concurrency` 別 (MiB/s)。

| 追加 RTT | c10 (既定) | c64 | c256 |
|---:|---:|---:|---:|
| 0 ms | **1,904** | 1,774 | 1,706 |
| 5 ms | **2,042** | 1,774 | 1,698 |
| 25 ms | 1,065 | **1,720** | 1,581 |
| 100 ms | 330 | **1,217** | 1,146 |

近いところでは既定の 10 が最良で、遠くなると 64 が最良になる。**100 ms で既定のまま
測れば 330 MiB/s、つまり実力の 27 % しか出ない。** 相手の既定値を測って「3.7 倍速い」と
書くのは比較ではない。

16 プロセスのほうは各プロセスが既定の 10 を持つので合計 160 になり、これは掃いていない。
100 ms で 16 プロセス (1,004) が 1 プロセス (1,217) を下回るのはそのためと思われる ──
160 本の要求が同時に走ると、遅い回線では取り合いになる。

## この回の限界

- **上の表の AEX2 は生バイトしか送っていない。** 可逆の deflate と誤差保証圧縮を
  使った場合は次の節にある
- **16 プロセスの `concurrency` は掃いていない** (各 10 の合計 160)。100 ms の
  zarr 16 プロセスは、絞れば今より上がる可能性がある
- 掃引の中に iPerf3 を挟んでいない。直後に測った 1 本は 28.8 Gbit/s と前の 26.1 より
  10.3 % 高かったが、続けて 3 回測ると 26.0 / 25.8 / 26.2 で、**外れ値であって
  帯域の移動ではない**と判断した。16 本 (162 → 167) は 3.1 % の差
- `mem.zarr` / `mem-shard.zarr` の `aexbench` 16 接続 (15,350) は 129 Gbit/s で、
  iPerf3 の 162 に近い。**リンクが効き始めている**ので下限と読むこと

## 生バイトの代わりに何を送るか

上の逆転は「AEX2 が 4 GiB を送り、HTTP が 123 MiB を送る」ことで起きた。AEX2 には
生バイト以外の選択肢が 2 つある ── 可逆の deflate (`arr.at(codec="gzip")`) と、
誤差保証圧縮 SZ3 (`arr.at(abs_error=...)`) である。どちらも**ストアはそのまま、
転送ごとに**選べる。何を買えて何を払うのかを測った (2026-09-22)。

### 条件 (この節のぶん)

| | 値 |
|---|---|
| REVISION | `661a88c` (両方、`sz` feature 付き) |
| フィクスチャ | `/mnt/aexram/wave.zarr` (1 GiB、131072 × 2048、4 MiB チャンク、格納 934 MB) |
| 同 (相手用) | `/mnt/aexram/wave-q2.zarr` (同じ場を `numcodecs.Quantize(2)` に通して格納、602 MB) |
| 帯域の制限 | netem の `rate` を両側に。その行の RTT は 10 ms |
| iPerf3 | 前 36.7 / 137、後 30.8 〜 37.9 / 170 Gbit/s (1 本 / 16 本) |
| 値 | n = 3 の中央値、1 GiB、AEX2 は 16 接続、zarr-python は 16 プロセス |

- **場は `wave.npy` と同じ**ものを Zarr にした。等差数列の `mem.zarr` に誤差上限を掛けると
  圧縮率が青天井になり実データについて何も言わない ([SZ3 の測定](benchmark-sz.md) と同じ理由)。
  実際、圧縮率は 8.7 / 10.9 / 73 倍で `wave.npy` の 8.72 / 10.93 / 72.71 倍と一致した
- **この節のどの行もリンクには当たっていない** (最速の 5,630 MiB/s = 47 Gbit/s に対し
  iPerf3 は 137 〜 170)。掃引の前後で 16 本が 24 % 動いているが、当たっていない以上
  結論には効かない。帯域を絞った行は netem の上限が律速である
- 届く精度は実測した。**上限はそのとおり守られる** (要求 1e-3 に対し最大誤差 1.000e-3、
  平均 4.3e-4)。`Quantize(2)` のストアは最大 3.906e-3

### 帯域が細い回線では SZ3 が答えになる

RTT 10 ms、netem で帯域を絞った。括弧内は zarr-python 比。

| 読み手 | 届く精度 | ワイヤ | 1 Gbit/s | 2 Gbit/s | 10 Gbit/s |
|---|---|---:|---:|---:|---:|
| zarr-python 16 プロセス | 無損失 | 956 MiB | 122 | 235 | 906 |
| AEX2 生バイト | 無損失 | 1,032 MiB | 112 | 221 | 944 |
| AEX2 deflate | 無損失 | 942 MiB | 122 (1.00) | 240 (1.02) | 578 (0.64) |
| AEX2 SZ3 1e-3 | 1.0e-3 | 118 MiB | **851 (7.0)** | 950 (4.0) | 945 (1.04) |
| AEX2 SZ3 1e-2 | 1.0e-2 | 94 MiB | **1,031 (8.4)** | 1,445 (6.1) | 1,479 (1.6) |
| AEX2 SZ3 1.0 | 1.0 | 14 MiB | **1,844 (15.1)** | 1,853 (7.9) | 1,886 (2.1) |

**1 Gbit/s では誤差上限 1e-3 で 7.0 倍、1.0 で 15.1 倍。** 圧縮した転送のスループットは
帯域にほとんど動かない (1e-3 で 851 → 950 → 945) ── 律速はリンクではなく圧縮する
コアだからで、[SZ3 の測定](benchmark-sz.md) が `.npy` で見たのと同じ形である。
**無損失の 3 つは帯域にそのまま比例する。**

10 Gbit/s では 1e-3 がようやく並ぶ (945 対 906)。つまり**この場では 10 Gbit/s あたりが
分岐点**で、それより細ければ誤差を売る価値があり、太ければ無い。

### deflate は「帯域が律速のとき」だけ効く

1 Gbit/s では deflate が生バイトを上回り (122 対 112)、zarr-python にちょうど並ぶ
(122 対 122)。無損失のまま、ワイヤのバイト数の不利が**消える**。

ところが**太い回線ではそうならない**。前節で zarr-python が勝った `mem.zarr` の
100 ms を、deflate で測り直した (4 GiB、n = 3、帯域は素のまま)。

| 追加 RTT | zarr-python 16 プロセス | AEX2 生バイト | AEX2 deflate |
|---:|---:|---:|---:|
| 0 ms | 7,909 | 12,150 | 2,803 |
| 25 ms | 5,745 | 4,992 | 2,329 |
| 100 ms | 2,121 | 1,693 | 1,406 |

deflate は**ワイヤを 4,102 → 139 MiB (29.5 倍)** に縮めているのに、100 ms でも
zarr-python に届かない。理由は in-flight の数え方にある: credit は**論理バイト**で
数えるので、圧縮しても**往復の回数は減らない**。減るのは 1 往復に載るバイト数だけで、
それが効くのはリンクが律速のときに限る。100 ms の太い回線で律速なのは往復の回数なので、
ここで効くのは圧縮ではなく in-flight を増やすこと (streams × credit × chunk) である。

同じことが SZ3 にも出ている。帯域無制限で RTT だけ振ると、圧縮しても伸びない。

| 追加 RTT | zarr-python | AEX2 生バイト | deflate | SZ3 1e-3 | SZ3 1e-2 | SZ3 1.0 |
|---:|---:|---:|---:|---:|---:|---:|
| 0 ms | 2,350 | **5,630** | 633 | 988 | 1,705 | 2,131 |
| 25 ms | 1,551 | 1,510 | 521 | 774 | 1,148 | 1,464 |
| 100 ms | 338 | 464 | 328 | 436 | 346 | 640 |

**近くて太い回線では圧縮は全部損である** (RTT 0 で 5,630 対 988、0.18 倍)。

### 相手にも精度を落とさせる

SZ3 は非可逆なので、無損失で読む zarr-python と並べるだけでは比較にならない。
zarr-python で同じ取引をするなら**保存の時点で精度を落とす** ── `numcodecs.Quantize` を
掛けて zstd で格納する。その `wave-q2.zarr` (最大誤差 3.906e-3) を同じように測った。

| 読み手 | 届く精度 | ワイヤ | 1 Gbit/s | 2 Gbit/s | 10 Gbit/s | 無制限 (RTT 0) |
|---|---|---:|---:|---:|---:|---:|
| zarr-python、quantize 済みストア | 3.9e-3 | 616 MiB | 187 | 354 | 1,346 | 2,282 |
| AEX2 SZ3 1e-3、**無損失ストア** | 1.0e-3 | 118 MiB | **851 (4.5)** | 950 (2.7) | 945 (0.70) | 988 |

**1 Gbit/s で 4.5 倍。しかも精度は AEX2 のほうが 4 倍細かく、ストアは無損失のままである。**
差の出どころはコーデックで、同じくらいの誤差で `Quantize` + zstd が 1.70 倍にしか
圧縮しないのに対し、SZ3 は 8.7 倍縮める (予測器が 2 次元の近傍を使うため)。

10 Gbit/s では逆転する (945 対 1,346)。そこでは SZ3 の圧縮する側の CPU が上限になり、
一方の zarr-python は縮んだストアをそのまま速く読めるからである。

### 代金は CPU である

1 GiB あたり、サーバとクライアントの両方 (`/proc/<pid>/stat` の差分)。

| 転送 | サーバ CPU | クライアント CPU | ワイヤ |
|---|---:|---:|---:|
| 生バイト | 2.0 s | 0.7 s | 1,025 MiB |
| deflate | 24.0 s | 4.9 s | 936 MiB |
| SZ3 1e-3 | 15.0 s | 7.4 s | 118 MiB |
| SZ3 1e-2 | 8.7 s | 5.2 s | 94 MiB |
| SZ3 1.0 | 6.8 s | 2.9 s | 14 MiB |

**deflate はいちばん高くていちばん縮まない** (この場では 1.09 倍)。浮動小数点の場に
汎用の可逆圧縮を掛けても仕方がないという、よく知られたことがそのまま出ている。
`mem.zarr` のような人工的に滑らかな列では 29.5 倍縮むが、それは実データの話ではない。

SZ3 は**上限が緩いほど安い** (15.0 → 6.8 s/GiB)。緩い上限では捨てる情報が多く、
予測が当たるぶん符号化も短いためである。

## この節の限界

- **ZFP は測っていない。** SZ3 との比較は [別の測定](benchmark-zfp.md) にある
- **zarr-python 側の非可逆は `Quantize` しか試していない。** `bitround` や、
  格納時に SZ3 を通す第三者コーデックは別の値を出す可能性がある
- **SZ3 は接続ごとに 1 スレッド**なので、上の値は 16 接続 = 16 コアのものである。
  接続数を変えれば分岐点も動く ([SZ3 の測定](benchmark-sz.md) の「分岐点はサーバの
  コア数で決まる」)
- 100 ms・帯域無制限で SZ3 1e-2 (346) が 1e-3 (436) を下回っているのは、
  そこでは 3 つとも往復の回数で律速されていて差が振れの中に入るためと見ている

## 再現方法

[eval-mdx2.md](eval-mdx2.md) の手順に従い、AEX2 サーバと nginx を両方立ててから、
クライアントの tmux で掃引を回す。

```console
$ ssh aex2-eval1 'sudo nginx -c /home/mdxuser/aex2/benchmarks/mdx2/nginx-zarr.conf'
$ ssh aex2-eval2 "tmux new-session -d -s remote 'cd aex2 &&
    SERVER=192.168.100.207 CLIENT=192.168.101.235 RTTS=0 COUNTERS=1 \
    STORES=\"mem-noisy.zarr mem.zarr mem-noisy-shard.zarr mem-shard.zarr\" \
    bash benchmarks/mdx2/zarr-remote-sweep.sh 5 2>&1 | tee ~/zarr-remote-a.txt'"
$ ssh aex2-eval2 "tmux new-session -d -s remote 'cd aex2 &&
    SERVER=192.168.100.207 CLIENT=192.168.101.235 RTTS=\"0 5 25 100\" \
    STORES=\"mem-noisy.zarr mem.zarr\" \
    bash benchmarks/mdx2/zarr-remote-sweep.sh 3 2>&1 | tee ~/zarr-remote-b.txt'"
```

両方の読み手が同じバイトを返すことは、測る前に確かめる。

```console
$ ssh aex2-eval2 "bash -lc 'cd ~/aex2 && for s in mem.zarr mem-noisy.zarr; do
    .venv/bin/python benchmarks/mdx2/zarr-procs.py http://192.168.100.207:8080/\$s \
      --via obstore --check aex:http://192.168.100.207:50391/\$s; done'"
```

圧縮した転送のほうは別の掃引で、帯域を絞る軸が主になる。フィクスチャを作り、
両方を `sz` feature 付きでビルドしてから回す。

```console
$ ssh aex2-eval1 "bash -lc 'cd ~/aex2 &&
    .venv/bin/python benchmarks/mdx2/mkzarr.py /mnt/aexram/wave.zarr 268435456 plain wave &&
    .venv/bin/python benchmarks/mdx2/mkzarr.py /mnt/aexram/wave-q2.zarr 268435456 plain wave 2'"
$ FEATURES=aex-server/hdf5,aex-server/sz,aex-client/sz benchmarks/mdx2/sync.sh
$ ssh aex2-eval2 "tmux new-session -d -s lossy 'cd aex2 &&
    SERVER=192.168.100.207 CLIENT=192.168.101.235 \
    bash benchmarks/mdx2/zarr-lossy-sweep.sh 3 2>&1 | tee ~/zarr-lossy.txt'"
```

`STORE` / `ELEMENTS` / `QUALITIES` を変えると別のストアにも当たる。`RATES` を空にするには
空文字ではなく空白を渡す (`${RATES:-...}` が既定値に戻してしまうため)。

```console
$ STORE=wave-q2.zarr QUALITIES="|--abs-error 0.01" bash benchmarks/mdx2/zarr-lossy-sweep.sh 3
$ STORE=mem.zarr ELEMENTS=1073741824 QUALITIES="|--codec gzip" RATES=" " \
    bash benchmarks/mdx2/zarr-lossy-sweep.sh 3
```

届く精度は転送してから確かめる。上限を要求しても、feature 無しのサーバは黙って
正確なデータを返す (`zarr-procs.py` はその場合その回を落とす)。

```python
import aex, numpy as np
c = aex.Client("http://192.168.100.207:50391")
a = c.open("wave.zarr")["array"]
exact = a[0:4096]
for eps in (0.001, 0.01, 1.0):
    print(eps, np.abs(a.at(abs_error=eps)[0:4096].astype("f8") - exact).max())
```

1 点だけ測るなら `zarr-procs.py` を直に呼ぶ。`--backend aex` は URL の最後の区切りまでを
制御プレーンの宛先、その後ろをストア名として読む。

```console
$ .venv/bin/python benchmarks/mdx2/zarr-procs.py \
    http://192.168.100.207:8080/mem-noisy.zarr --via obstore --concurrency 64 --procs 1 16
$ .venv/bin/python benchmarks/mdx2/zarr-procs.py \
    http://192.168.100.207:50391/mem-noisy.zarr --backend aex --streams 16 --procs 1
```
