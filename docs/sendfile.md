# `sendfile` は効くか

効かない。正確には、**逐次に読んで送る実装より 35〜45 % 速いが、いま実装されている
「読みと送りを重ねる」方式より遅い**。測定日 2026-09-16、環境は
[M2 の測定](benchmark-m2-local.md#測定環境) と同一。

SPEC §6.5.1 は `sendfile` を採らないと決めているが、その理由は将来の拡張性
(圧縮バックエンドや適応品質を入れた時点で効かなくなる) であって、性能そのものでは
なかった。ここでは性能の側から確かめる。

## 測定

ループバックのソケットへ 4 GiB を送る。3 つの方式が**同じ受信側**へ、同じ大きさの
断片で、各断片の前に 32 バイトのヘッダを付けて送る。違いはペイロードの運び方だけ。

| 断片 | 逐次に読んで送る | 読みと送りを重ねる (現行) | `sendfile` |
|---:|---:|---:|---:|
| 512 KiB | 9,385 MiB/s | **18,732 MiB/s** | 12,785 MiB/s |
| 4 MiB | 9,531 MiB/s | **14,134 MiB/s** | 13,389 MiB/s |

CPU は GiB あたり、逐次 0.16 s、重ねる 0.16〜0.20 s、`sendfile` **0.12〜0.13 s**。

(受信側は使い回すバッファへ読んで捨てるだけなので、絶対値は端から端までの測定より
高く出る。3 方式の比較としては同条件である。)

## なぜ `sendfile` が負けるのか

`sendfile` は**1 本のスレッドが 1 度に 1 つのことをする**。ページキャッシュから
ソケットへ、1 回の呼び出しで運ぶ。重ねる余地がない。

現行方式は 2 本のスレッドが同時に働く。片方がページキャッシュから次の断片を読み、
もう片方が前の断片をソケットへ書く。**1 バイトあたりのコピーは `sendfile` より
1 回多いが、それを 2 つのコアで並行に行う。** このマシンではそちらが勝つ。

`sendfile` が勝つのは CPU である。コピーが 1 回少ないぶん、GiB あたり 0.12 s と
現行の 0.16 s より 25 % 少ない。**メモリ帯域ではなく CPU が希少な環境なら話は変わる。**

## 実ネットワークではどうか

ここで比べているのはどれも 10,000 MiB/s 以上であり、**10 GbE (1,192 MiB/s) の
8 倍以上**である。リンクが律速する環境では 3 方式とも同じ速度、すなわちリンク速度に
なる。差が出るのは CPU 使用率だけで、それも「少数クライアント」前提では逼迫しない。

実 NIC では `sendfile` が真のゼロコピー (NIC がページキャッシュから DMA) になりうる
ので CPU の差はさらに開くが、**スループットはどのみちリンクで頭打ちになる**。

## 採らない理由 (変更なし)

性能上の理由が加わっただけで、SPEC §6.5.1 の判断は変わらない。

1. **現行方式より遅い。** 上の測定のとおり
2. **効く範囲が狭い。** 非圧縮・無加工の転送にしか使えない。Zarr / HDF5 は圧縮
   チャンクが前提で、伸長結果はバッファに載る。適応品質 (dtype キャスト、間引き、
   誤差上限付き圧縮) を入れた時点で加工経路が主になる。**初版の `.npy` にしか効かず、
   将来消える最適化**である
3. **恒久的な複雑さを抱える。** バックエンドごとの分岐、`IoSlice` のライフタイム、
   OS 分岐。`ArrayDataset::read_range` が「呼び出し側のバッファに書くだけ」で済んで
   いる設計が崩れる

なお `sendfile` の引数の意味は OS ごとに違う。macOS は**ヘッダの長さを送信長に
含める**が、FreeBSD は別勘定である。移植性の面でも安くはない。

## 再検討するとすれば

- **CPU が律速だと分かったとき。** 25 % の CPU 削減には価値がある。ただしそれは
  「多クライアント」の話であり、本基盤の前提ではない
- **100 GbE 級で、かつ非圧縮の `.npy` しか扱わないと分かったとき**

どちらも SPEC §7.1 の言うとおり、`fn zero_copy_source(&self, ...) -> Option<(RawFd, u64)>`
のような任意実装のメソッドを足せば、フレームプロトコルもトレイトも変えずに後から
載せられる。

## 再現方法

```console
$ cargo build --release -p aex-bench
$ for m in pread pread-threaded sendfile; do
>   target/release/sendfilebench /path/to/arr.npy \
>       --bytes $((4<<30)) --piece $((512*1024)) --reps 5 --mode $m
> done
```
