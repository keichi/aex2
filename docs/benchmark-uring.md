# io_uring は効くか (poolbench による予備測定)

[io_uring の計画](io-uring-plan.md) の手順 0。サーバを改修する前に、送信経路だけを
切り出した `poolbench` で効果を確かめた。測定日 2026-09-18。

## 結論

**この環境では採らない。** ゼロコピー送信は送信側 CPU を 3〜4 割減らすが、
**その CPU はどの接続数でも律速ではなく**、読みをリングに載せると 8 接続以上で
逐次 (現行の `read_buffers = 1`) に 24〜40 % 負ける。

- **ゼロコピー送信は本物だった。** virtio NIC 上でコピーへの後退は 0 回
  (`IORING_SEND_ZC_REPORT_USAGE` で確認)、`ENOBUFS` も 0 回。送信側 CPU は
  GiB あたり 0.48 s → 0.32 s。`perf` でも送信ページの確保とゼロ埋め
  (`clear_page_erms`) と `writev` のコピー (`_copy_from_iter`) が消える。
  判定基準「25 % 以上減る」は満たす
- **しかし速くならない。** 16 接続では逐次が 14,359 MiB/s で、これは iPerf3 の
  16 本 (15,600〜17,200 MiB/s) の 83〜92 % にあたる。**逐次はすでに回線を埋めており**、
  送信側 CPU を削っても埋める先がない。リング送信は 1 接続につき送信 SQE を 1 つに
  制限するため (順序の約束)、完了を刈って次を積むまでソケットが空く。
  `MSG_WAITALL` を付けても傾向は変わらなかった
- **メモリ常駐では、リングに載せた読みが負ける。** 判定基準「tmpfs で `serial` の
  ±3 % 以内」は 8 接続で −24 %、16 接続で −40 % と、大きく外れる。原因は `perf` が
  示す: **tmpfs の読みは投入したスレッドでは完了せず、io-wq のカーネルスレッドに
  回される** (`iou-wrk-*` が `_copy_to_iter` を実行している)。計画が避けようとした
  スレッド間の受け渡しが、カーネルの中に戻ってくる
- **効くのはコールドディスクで接続数が少ないときだけ。** 4 接続で 1,865 → 2,546
  (+37 %)、8 接続で 2,169 → 2,715 (+25 %)。ただし [M6](benchmark-m6.md) と
  [共有読みプール](benchmark-read-pool.md) の結論と同じで、**接続を増やせば同じ効果が
  受け渡しなしで得られる** (逐次 16 接続のコールドは過去の測定で 2,513)
- 先読み深さは 4 か 8。1 と 2 は明確に遅い

したがって計画の段階 1・段階 2 とも着手しない。作った `poolbench` のモードは、
環境が変わったとき (ベアメタル、NVMe、送信側 CPU が律速になる多クライアント) に
測り直せるよう残す。

## 条件

- サーバ `aex2-eval-1`、クライアント `aex2-eval-2`。構成は [eval-mdx2.md](eval-mdx2.md)
  (16 vCPU / 31 GiB、kernel 6.8.0-136、virtio NIC、RTT 0.7 ms、MTU 1442)
- `REVISION`: `a995520`。Rust 1.98.1
- iPerf3 (server → client、`-R`): 掃引の直前 26.1 / 131 Gbit/s、直後 26.6 / 144 Gbit/s
  (1 本 / 16 本)。1 本は 2 % 以内。**16 本は 10 % 動いた**ので、16 接続の絶対値は
  幅を持って読むこと。条件どうしは各周で交互に測っているので比較は成り立つ
- sysctl は既定のまま (`net.core.wmem_max = 212992`、cubic)。netem なし
- 1 点 4 GiB を 1 回、全条件を 1 巡する組を 5 周。表は 5 周の中央値、単位は MiB/s
- 同じ掃引を 2 回行った (1 回目はリング送信に `MSG_WAITALL` を付けていない)。
  傾向は両方で同じ。表は 2 回目のもの

## 何を比べたか

`poolbench send` が `.npy` を 512 KiB ずつ読み、32 バイトのヘッダと一緒に送る。
`poolbench sink` が受けて捨てる。4 GiB を接続数で等分する。

| 方式 | スレッド | 読み | 送り | 相当 |
|---|---|---|---|---|
| `serial` | 接続数 | `pread` | `writev` | 現行 (`read_buffers = 1`) |
| `pair` | 接続数 × 2 | `pread` | `writev` | `read_buffers = 3` |
| `uring` | 接続数 | ring (`READ`) | `writev` | 計画の段階 1 |
| `uring-copy` | 接続数 | ring | ring (`SEND`) | 段階 2、5.15 相当 |
| `uring-zc` | 接続数 | ring | ring (`SEND_ZC`) | 段階 2 |

リングは接続スレッド自身が持ち、自身が刈る。`--depth` 枚のバッファを先行して読み、
送りは piece の offset 順、送信 SQE は 1 接続に 1 つまで。

FETCH の往復もチケット検証も含まない。`sink` は使い回すバッファへ読んで捨てるだけで、
本物のクライアント (0.29〜0.31 s/GiB) よりずっと軽い。

virtio ディスク上の 4 GiB。実行ごとに `posix_fadvise(DONTNEED)`。

|---:|---:|---:|---:|---:|
| 1 | 1,119 | **1,257** | 1,221 | 1,165 |
| 4 | 1,865 | 1,847 | **2,546** | 2,423 |

送信側 CPU は serial 0.83〜0.88、pair 0.92〜1.00、`uring` 0.82〜0.87、
`uring-zc` 0.61〜0.69 s/GiB。

ここだけは計画の仮説どおりで、**同時に走る読みの数**がスループットを決める。
1 接続では深さ 4 でも伸びず、pair (読みスレッド 1 本 + バッファ 3 枚) と同程度に
留まる。

## `perf` が示すもの

8 接続、tmpfs、機械全体のサンプル (idle を含む)。上位のカーネル関数だけを挙げる。

| 関数 | serial | uring-zc |
|---|---:|---:|
| `_copy_to_iter` (読みのコピー) | 8.4 % | 7.1 % (**io-wq スレッド上**) |
| `clear_page_erms` (送信ページの確保とゼロ埋め) | 6.1 % | — |
| `_copy_from_iter` (送信のコピー) | 2.1 % | — |

2 つのことが読み取れる。

1. **ゼロコピー送信は約束どおり効く。** 送信側のページ確保とコピーが消える。
   これが CPU 0.48 → 0.32 s/GiB の中身である
2. **読みは投入したスレッドで完了していない。** tmpfs (shmem) の読みは io-wq の
   カーネルスレッド (`iou-wrk-*`) に回され、そこでコピーされる。「接続スレッド自身が
   投入し自身が刈るので受け渡しがない」という計画の前提が、**メモリ常駐データでは
   成り立たない**。計画は §8 でネットワーク FS の io-wq を危険として挙げていたが、
   実際には tmpfs でも起きる

## 判定基準への答え

計画 §5.3 の表に答える。

| 問い | 結果 |
|---|---|
| 段階 1 は入れる価値があるか | **否**。tmpfs で 8 接続 −24 %、16 接続 −40 % (基準は ±3 % 以内)。コールドは 4 接続以上で pair 以上という条件は満たす |
| ゼロコピー送信は効くか | **CPU には効く**。送信側 0.48 → 0.32 s/GiB (−33 %、基準は −25 %)。速度には効かない |
| 接続 1 本あたりの速度は伸びるか | **伸びない**。1 接続の tmpfs で `uring-zc` は逐次と同程度かそれ以下 |
| worker モデルは損をしないか | **測っていない** (段階 2 の worker 割り当ては実装していない) |
| 5.15 で段階 2 を入れる価値があるか | **測っていない** (OCTOPUS では測っていない) |

## 測っていないこと

- **OCTOPUS (kernel 5.15) と Lustre。** 6.8 の VM で負けたものを 5.15 で測る理由は薄い
- **worker モデル (段階 2 の後半)。** 1 接続 1 スレッドのまま測った。worker に
  まとめる価値は「同じコア数でより多くの接続を捌く」ことだが、この VM では
  逐次のスレッドが CPU で詰まっていない (16 接続で機械全体の 6 コア相当)
- **ベアメタルと NVMe。** 起床が安く、`io_uring` の投入が inline で完了しやすい
  環境では結果が変わりうる
- **送信側 CPU が律速になる状況。** 多クライアント、あるいは受信側が十分に速い
  構成では、ゼロコピー送信の 3 割引きが意味を持つ。そのときに測り直す価値はある
- **`O_DIRECT` と `extents`。** コールドで効く可能性は残るが、この結果では
  リング化そのものの価値が立たないので試していない

## 再現方法

```console
$ benchmarks/mdx2/sync.sh
$ benchmarks/mdx2/uring-sweep.sh 5 | tee ~/uring-sweep.txt
$ ssh aex2-eval2 'cat ~/logs/uring-sink.log'      # 受信側の CPU。送信側と同じ順
```

1 条件だけ測るなら次のとおり。`--verify` はリング経由で読んだ各 piece を
`pread` の結果と突き合わせる (性能測定では外す)。

```console
$ poolbench sink                                                    # eval-2
$ poolbench send /mnt/aexram/mem.npy --to 192.168.101.235:50399 \
      --bytes $((4<<30)) --streams 8 --mode uring-zc --depth 4      # eval-1
```
