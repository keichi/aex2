# mdx2: Zarr バックエンドの転送性能と sharding

Zarr バックエンド (SPEC §7.6) が、チャンク 1 個 = ファイル 1 個という別種の
ストレージ構造でも接続数で伸びるか、そして sharding がその `open` の回数を
減らすことで効くかを mdx2 の VM 2 台で測った記録である。測定日 2026-09-21。

## 結論

1. **tmpfs では sharding に差が無い。** 同じチャンクをファイル 1024 個で持つか
   16 個で持つかで、転送速度は変わらない (比は 0.974〜1.060、符号も一定せず、
   各条件の振れの内側)。tmpfs の `open` にディスク I/O が伴わないので、
   **ファイル数はそのままでは律速ではない**
2. **コールドな virtio ディスクでは sharding が効く。** 測った 6 通りすべてで
   shard のほうが速く、**+2.7 〜 +9.4 %**。tmpfs と違って符号が一定なので、
   小さいが実在する差である。逆に言えば、**この構造で払う代償はその程度**で、
   1024 ファイルでも転送が壊れるわけではない
3. **Zarr は `.npy` より接続数で伸びる。** 1 → 16 接続で `.npy` が 6.9 倍なのに対し
   Zarr は **9.4 〜 11.2 倍**。伸長は接続ごとの CPU 仕事なので並列に走るが、
   `.npy` は 16 接続で既にリンクを飽和している (17,420 MiB/s ≒ iPerf3 の 140 Gbit/s)。
   16 接続での到達点は `.npy` 比で counting 69〜71 %、noisy 39〜42 %
4. **同じストアを持っているマシンの上で zarr-python に読ませるより、
   ネットワーク越しの AEX2 のほうが 3.4 〜 9.0 倍速い。** zarr-python は
   `async.concurrency = 10` で並列に取りに行っているので単スレッドの比較ではない。
   1 接続どうしなら同程度 (AEX2 1,267 対 zarr-python 1,865 MiB/s) で、
   **差は接続数でスケールするかどうかから来ている**
5. **zarr-python は shard を読むと遅くなる** (1,865 → 1,338 MiB/s)。
   `shards=` を指定すると zarr-python 自身が「partial reads and writes を無効にする」と
   警告する。AEX2 は shard でも落ちない (12,308 → 12,014、振れの内側)

## 条件

環境は [mdx2 の測定](benchmark-mdx2.md#測定環境) と同じ。手順は
[eval-mdx2.md](eval-mdx2.md) に従った。

| | 値 |
|---|---|
| サーバ / クライアント | `aex2-eval-1` / `aex2-eval-2` |
| REVISION | `efe51cc` (両方) |
| サーバ設定 | `benchmarks/mdx2/aex-decode-cache-64m.toml` (制御 50391) |
| クライアント | `aexbench --prefault`、4 GiB、既定のチャンク (4 MiB)、credit 16 |
| Rust / iPerf3 / kernel | 1.98.1 / 3.16 / 6.8.0-136 |
| zarr-python / numcodecs | 3.4.0 / 0.17.0 (`async.concurrency = 10`) |
| sysctl | 既定 (`wmem_max = 212992`、cubic) |

デコードキャッシュを 64 MiB (16 接続 × 4 MiB) に絞ったサーバで測った。既定の 1 GiB だと
1024 チャンクのうち 256 個が前の回から残り、伸長する区間とキャッシュから写すだけの区間が
混ざる。この設定では毎回ほぼ全チャンクを伸長する ([HDF5 の測定](benchmark-hdf5.md) と同じ理由)。

`/mnt/aexram` は既存のフィクスチャで 94 % 埋まっていたので、**12 → 20 GiB に張り直した**
(`sudo mount -o remount,size=20G /mnt/aexram`)。fstab には無いので再起動で消える。

### データ

論理サイズはすべて 2^30 要素 (4 GiB) の float32。作り方は
[eval-mdx2.md](eval-mdx2.md#データの置き場所) にある。Zarr はチャンク 4 MiB、
shard は 256 MiB (内部チャンク 64 個)、コーデックは zarr-python の既定 (zstd)。

| ラベル | パス | 中身 | 格納サイズ | ファイル数 |
|---|---|---|---:|---:|
| npy | `mem.npy` | 要素 i の値が i | 4.0 GiB | 1 |
| zarr | `mem.zarr` | 同上、4 MiB チャンク | 125 MB (3.0 %) | 1,026 |
| zarr-shard | `mem-shard.zarr` | 同じチャンクを 256 MiB の shard に | 123 MB | 18 |
| zarr-noisy | `mem-noisy.zarr` | `i % 1000` + 0〜15 の乱数 | 1.4 GB (35 %) | 1,026 |
| zarr-noisy-shard | `mem-noisy-shard.zarr` | 同上を shard に | 1.4 GB | 18 |

ディスクの回 (`~/disk/disk*.zarr`) は同じものを virtio ディスクに置いたもの。
ファイル数 1,026 のうち 2 個は `zarr.json` (ルートと配列)、shard の 18 個のうち
2 個も同じ。**比べてよいのは plain と shard の対だけ**である ── 格納サイズが
同じで、違うのはファイル数だけだからで、`.npy` との比較は格納バイト数が
30 倍違うので I/O 量が違う。

| 回 | 前後の iPerf3 (`-R`、1 本 / 16 本、Gbit/s) |
|---|---|
| tmpfs | 27.2 → 27.9 / 144 → 140 |
| ディスク | 27.9 → 25.0 / 140 → 146 |

ディスクの回は 1 本が 10.4 % 動いており、手順の決まりでは測り直しに当たる。
ただし**この回はディスク律速**で、いちばん速い条件でも 11,049 MiB/s = 92.7 Gbit/s と
リンクに届いていない。1 接続の条件に至っては 10 Gbit/s 前後である。plain と shard は
**1 巡ごとに交互に**測っており、差は 6 通りすべてで同じ符号なので、結論は帯域の
振れに依存しない。16 本は 4.3 % 以内。

## 結果

### tmpfs (メモリ常駐)

値は中央値 (MiB/s)、括弧内は最小〜最大、n = 5。

| 接続数 | npy | zarr | zarr-shard | zarr-noisy | zarr-noisy-shard |
|---:|---:|---:|---:|---:|---:|
| 1 | 2,529 (1,854〜2,551) | 1,267 (1,107〜1,276) | 1,276 (1,111〜1,313) | 659 (614〜709) | 646 (622〜708) |
| 2 | 4,152 (3,577〜4,560) | 2,206 (2,173〜2,550) | 2,290 (2,226〜2,394) | 1,280 (1,268〜1,312) | 1,294 (1,276〜1,387) |
| 4 | 8,494 (7,937〜9,608) | 4,534 (4,465〜4,722) | 4,658 (4,620〜4,880) | 2,530 (2,482〜2,645) | 2,491 (2,478〜2,579) |
| 8 | 14,836 (13,750〜15,706) | 8,289 (7,707〜8,607) | 8,072 (7,548〜8,579) | 4,498 (4,398〜4,683) | 4,443 (4,390〜4,713) |
| 16 | 17,420 (16,705〜17,983) | 12,308 (10,312〜12,367) | 12,014 (11,696〜13,242) | 6,826 (6,532〜7,262) | 7,235 (6,877〜7,862) |

shard / plain の比は counting で 1.007 / 1.038 / 1.027 / 0.974 / 0.976、
noisy で 0.980 / 1.011 / 0.985 / 0.988 / 1.060。**符号が一定しない**。

1 → 16 接続の伸びは npy 6.9 倍、zarr 9.7 倍、zarr-shard 9.4 倍、
zarr-noisy 10.4 倍、zarr-noisy-shard 11.2 倍。

### コールドな virtio ディスク

各回の前に、そのストアの全ファイルのページを `dropcache` で落としている。
値は中央値 (MiB/s)、括弧内は最小〜最大、n = 5。

| 接続数 | npy | zarr | zarr-shard | 比 | zarr-noisy | zarr-noisy-shard | 比 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 1,386 (1,278〜1,397) | 1,148 (1,041〜1,208) | 1,256 (1,209〜1,281) | **1.094** | 562 (474〜566) | 578 (463〜582) | **1.028** |
| 4 | 2,073 (1,763〜2,171) | 4,152 (1,979〜4,382) | 4,264 (3,817〜4,424) | **1.027** | 1,969 (1,524〜2,013) | 2,046 (1,978〜2,076) | **1.039** |
| 16 | 2,478 (2,202〜2,606) | 10,326 (10,018〜10,523) | 11,049 (10,372〜11,879) | **1.070** | 5,278 (5,133〜5,421) | 5,753 (5,660〜5,828) | **1.090** |

各条件の 1 回目だけ低く出る (例: 4 接続の zarr が 1,979、以降は 4,000 前後)。
2 回目以降は安定しており、中央値は影響を受けていない。

**`.npy` はディスクが律速で接続数に伸びない** (1,386 → 2,478、1.8 倍)。
圧縮された Zarr は読むバイト数が 1/30 〜 1/3 なので、同じ 4 GiB を届けるのに
ディスクから読む量が桁違いに少なく、16 接続で `.npy` の 4.2 倍出る。
**これは圧縮の結果であって sharding の結果ではない。**

### zarr-python との比較 (ストアを持っているマシンの上、tmpfs、warm)

| ストア | zarr-python | AEX2 1 接続 | AEX2 16 接続 | 16 接続 / zarr-python |
|---|---:|---:|---:|---:|
| `mem.zarr` | 1,865 (1,287〜1,878) | 1,267 | 12,308 | **6.6 倍** |
| `mem-shard.zarr` | 1,338 (1,211〜1,382) | 1,276 | 12,014 | **9.0 倍** |
| `mem-noisy.zarr` | 1,986 (1,714〜2,287) | 659 | 6,826 | **3.4 倍** |
| `mem-noisy-shard.zarr` | 1,212 (1,053〜1,251) | 646 | 7,235 | **6.0 倍** |

zarr-python は `z[:]` で全体を読んだ時間。n = 5 の中央値。**ネットワークを渡らない**
ローカル読みであり、AEX2 の側は VM 間を渡ってクライアントのバッファに届くまでの
時間である。

## 再現方法

[eval-mdx2.md](eval-mdx2.md) のデータ作成 (`mkzarr.py`) を済ませ、
`aex-decode-cache-64m.toml` のサーバを立ててから、クライアントで次を回した。

```console
$ ssh aex2-eval2 "bash -lc 'cd aex2 && S=http://192.168.100.207:50391
  for r in 1 2 3 4 5; do for s in 1 2 4 8 16; do
    for f in mem.npy mem.zarr mem-shard.zarr mem-noisy.zarr mem-noisy-shard.zarr; do
      case \$f in *noisy*) p=none ;; *) p=counting-f32 ;; esac
      target/release/aexbench \$S \$f --bytes \$((4<<30)) --streams \$s \
        --reps 1 --prefault --pattern \$p --label \$f
    done; done; done'"
```

ディスクの回は、各回の前にそのストアのページをサーバ側で落とす。`find -type f` が
`.npy` の 1 個も、ストアの全チャンクも同じように並べてくれる。

```console
$ ssh 192.168.100.207 "cd aex2 && target/release/dropcache \$(find ~/disk/\$f -type f)"
```

zarr-python の比較はサーバ上で次を実行した。

```python
import statistics, time, zarr
for path in ["/mnt/aexram/mem.zarr", "/mnt/aexram/mem-noisy.zarr",
             "/mnt/aexram/mem-shard.zarr", "/mnt/aexram/mem-noisy-shard.zarr"]:
    z = zarr.open_array(f"{path}/array", mode="r")
    runs = []
    for _ in range(5):
        t = time.perf_counter()
        out = z[:]
        runs.append(4096.0 / (time.perf_counter() - t))
        del out
    print(path, statistics.median(runs))
```
