# mdx2: Zarr バックエンドの転送性能と sharding

Zarr バックエンド (SPEC §7.6) が、チャンク 1 個 = ファイル 1 個という別種の
ストレージ構造でも接続数で伸びるか、そして sharding がその `open` の回数を
減らすことで効くかを mdx2 の VM 2 台で測った記録である。測定日 2026-09-21。

## 結論

1. **tmpfs では sharding に差が無い。** 同じチャンクをファイル 1024 個で持つか
   16 個で持つかで、転送速度は変わらない (比は 0.974〜1.060、符号も一定せず、
   各条件の振れの内側)。tmpfs の `open` にディスク I/O が伴わないので、
   **ファイル数はそのままでは律速ではない**
2. **コールドな virtio ディスクでは sharding が効く。** 測った 6 通りすべてで
   shard のほうが速く、**+2.7 〜 +9.4 %**。tmpfs と違って符号が一定なので、
   小さいが実在する差である。逆に言えば、**この構造で払う代償はその程度**で、
   1024 ファイルでも転送が壊れるわけではない
3. **Zarr は `.npy` より接続数で伸びる。** 1 → 16 接続で `.npy` が 6.9 倍なのに対し
   Zarr は **9.4 〜 11.2 倍**。伸長は接続ごとの CPU 仕事なので並列に走るが、
   `.npy` は 16 接続で既にリンクを飽和している (17,420 MiB/s ≒ iPerf3 の 140 Gbit/s)。
   16 接続での到達点は `.npy` 比で counting 69〜71 %、noisy 39〜42 %
4. **1 コアあたりでは zarr-python にわずかに負けており、原因は分かっている。**
   16 接続で 467 対 481 〜 490 MiB/s。サーバの `perf` を見ると伸長に使えているのは
   CPU の 6 割で、残りは写しとページの世話である。チャンクごとに 4 MiB を確保し
   直しているのが効いていて、glibc に mmap を使わせないだけで **+23 %**
   (6,746 → 8,483 MiB/s、1 コアあたり 467 → 537) になる。**直せば zarr-python を
   1 割上回る。**「Rust だから速い」のではない
5. **速いのはコーデックではなく、1 つの要求で何コア使えるかである。**
   1 コアあたりの処理量は AEX2 472 〜 627、zarr-python 481 〜 490 MiB/s で
   **ほぼ同じ** (noisy、伸長が主)。違うのは、AEX2 の 1 要求が 14.4 コアを回すのに対し、
   zarr-python の 1 プロセスは **3.0 〜 3.7 コアで頭打ち**になることである。
   呼び出し側のスレッドを 16 本に増やしても伸びず、**プロセスを分けると伸びる**
   ── 限界は 1 つのインタプリタの中にある
6. **したがって比較は 2 通り書く必要がある。** 素直に書いた zarr-python
   (1 プロセス) に対しては **3.1 〜 9.0 倍**。マシン全体を使わせた zarr-python
   (16 プロセス) に対しては **1.16 〜 1.63 倍**で、しかも AEX2 だけが
   ネットワークを渡っている
7. **zarr-python は shard を読むと遅くなる** (2,500 → 1,338 MiB/s)。
   `shards=` を指定すると zarr-python 自身が「partial reads and writes を無効にする」と
   警告する。AEX2 は shard でも落ちない (12,308 → 12,014、振れの内側)。
   **AEX2 の取り分がいちばん大きいのは shard のとき** (16 プロセス比で 1.60 〜 1.63 倍)

## 条件

環境は [mdx2 の測定](benchmark-mdx2.md#測定環境) と同じ。手順は
[eval-mdx2.md](eval-mdx2.md) に従った。

| | 値 |
|---|---|
| サーバ / クライアント | `aex2-eval-1` / `aex2-eval-2` |
| REVISION | `efe51cc` (両方) |
| サーバ設定 | `benchmarks/mdx2/aex-decode-cache-64m.toml` (制御 50391) |
| クライアント | `aexbench --prefault`、4 GiB、既定のチャンク (4 MiB)、credit 16 |
| Rust / iPerf3 / kernel | 1.98.1 / 3.16 / 6.8.0-136 |
| zarr-python / numcodecs | 3.4.0 / 0.17.0 (`async.concurrency = 10`) |
| sysctl | 既定 (`wmem_max = 212992`、cubic) |

デコードキャッシュを 64 MiB (16 接続 × 4 MiB) に絞ったサーバで測った。既定の 1 GiB だと
1024 チャンクのうち 256 個が前の回から残り、伸長する区間とキャッシュから写すだけの区間が
混ざる。この設定では毎回ほぼ全チャンクを伸長する ([HDF5 の測定](benchmark-hdf5.md) と同じ理由)。

`/mnt/aexram` は既存のフィクスチャで 94 % 埋まっていたので、**12 → 20 GiB に張り直した**
(`sudo mount -o remount,size=20G /mnt/aexram`)。fstab には無いので再起動で消える。

### データ

論理サイズはすべて 2^30 要素 (4 GiB) の float32。作り方は
[eval-mdx2.md](eval-mdx2.md#データの置き場所) にある。Zarr はチャンク 4 MiB、
shard は 256 MiB (内部チャンク 64 個)、コーデックは zarr-python の既定 (zstd)。

| ラベル | パス | 中身 | 格納サイズ | ファイル数 |
|---|---|---|---:|---:|
| npy | `mem.npy` | 要素 i の値が i | 4.0 GiB | 1 |
| zarr | `mem.zarr` | 同上、4 MiB チャンク | 125 MB (3.0 %) | 1,026 |
| zarr-shard | `mem-shard.zarr` | 同じチャンクを 256 MiB の shard に | 123 MB | 18 |
| zarr-noisy | `mem-noisy.zarr` | `i % 1000` + 0〜15 の乱数 | 1.4 GB (35 %) | 1,026 |
| zarr-noisy-shard | `mem-noisy-shard.zarr` | 同上を shard に | 1.4 GB | 18 |

ディスクの回 (`~/disk/disk*.zarr`) は同じものを virtio ディスクに置いたもの。
ファイル数 1,026 のうち 2 個は `zarr.json` (ルートと配列)、shard の 18 個のうち
2 個も同じ。**比べてよいのは plain と shard の対だけ**である ── 格納サイズが
同じで、違うのはファイル数だけだからで、`.npy` との比較は格納バイト数が
30 倍違うので I/O 量が違う。

| 回 | 前後の iPerf3 (`-R`、1 本 / 16 本、Gbit/s) |
|---|---|
| tmpfs | 27.2 → 27.9 / 144 → 140 |
| ディスク | 27.9 → 25.0 / 140 → 146 |

ディスクの回は 1 本が 10.4 % 動いており、手順の決まりでは測り直しに当たる。
ただし**この回はディスク律速**で、いちばん速い条件でも 11,049 MiB/s = 92.7 Gbit/s と
リンクに届いていない。1 接続の条件に至っては 10 Gbit/s 前後である。plain と shard は
**1 巡ごとに交互に**測っており、差は 6 通りすべてで同じ符号なので、結論は帯域の
振れに依存しない。16 本は 4.3 % 以内。

**これは圧縮の結果であって sharding の結果ではない。**

### zarr-python との比較 (ストアを持っているマシンの上、tmpfs、warm)

zarr-python は `z[:]` で全体を読んだ時間。**ネットワークを渡らない**ローカル読みで、
AEX2 の側は VM 間を渡ってクライアントのバッファに届くまでの時間である。
「1 プロセス」は各ストアで測った 2 通り (`z[:]` を繰り返す形と、プロセスを
起こして 1 回読む形) の**速いほう**を採った。

| ストア | zarr-python 1 プロセス | zarr-python 16 プロセス | AEX2 1 接続 | AEX2 16 接続 | 対 1 プロセス | 対 16 プロセス |
|---|---:|---:|---:|---:|---:|---:|
| `mem.zarr` | 2,500 | 10,574 | 1,267 | 12,308 | 4.9 倍 | **1.16 倍** |
| `mem-shard.zarr` | 1,338 | 7,387 | 1,276 | 12,014 | 9.0 倍 | **1.63 倍** |
| `mem-noisy.zarr` | 2,169 | 5,573 | 659 | 6,826 | 3.1 倍 | **1.22 倍** |
| `mem-noisy-shard.zarr` | 1,212 | 4,525 | 646 | 7,235 | 6.0 倍 | **1.60 倍** |

**1 接続どうしでは AEX2 のほうが遅い。** 1 接続の AEX2 は伸長 1 コア分そのもので、
そこにネットワークの送受信が乗る。差が出るのは接続数を増やしたときだけである。

## なぜ zarr-python より速いのか

「コーデックが速いから」ではない。順に切り分ける。

### 1 コアの天井は両者ほぼ同じ

`/proc/<pid>/stat` の utime + stime から、サーバが 1 GiB 届けるのに使った CPU 時間を
出した (1 条件 12 GiB)。zarr-python 側は `time.process_time()` (プロセス全体)。

| | MiB/s | CPU s/GiB | 1 コアあたり MiB/s | 使っているコア数 |
|---|---:|---:|---:|---:|
| AEX2 1 接続 (noisy) | 634 | 1.63 | 627 | 1.0 |
| AEX2 16 接続 (noisy) | 6,785 | 2.17 | 472 | 14.4 |
| AEX2 1 接続 (counting) | 1,301 | 0.79 | 1,300 | 1.0 |
| AEX2 16 接続 (counting) | 11,555 | 1.25 | 821 | 14.1 |
| zarr-python 1 プロセス (noisy) | 1,461〜1,817 | 2.09〜2.13 | 481〜490 | **3.0〜3.7** |

**1 コアあたりは 472 〜 627 対 481 〜 490 MiB/s でほぼ並ぶ。** AEX2 のほうは
ネットワークへの送信も込みなので、伸長そのものの速さに差は無いと見てよい。
参考として、numcodecs の zstd で 1 チャンクを伸長し続けると 1 コア
1,117 〜 1,124 MiB/s 出る ── AEX2 の 1 接続 (627) も zarr-python (481〜490) も、
その 4 〜 6 割を枠組みの仕事に使っている。

zarr-python 側は**独立に 2 回**回した。スループットは回ごとに 10 〜 20 % 振れるが、
CPU s/GiB は 2.09 と 2.13 で安定しており、下の掃引の形も変わらない。
ここで信用してよいのは 1 コアあたりの値と形であって、スループットの絶対値ではない。

### zarr-python は 1 プロセスで 3 コア強しか使えない

呼び出し側のスレッドを増やしても変わらない。

| 呼び出しスレッド数 | 1 | 2 | 4 | 8 | 16 |
|---|---:|---:|---:|---:|---:|
| MiB/s、1 回目 | 1,817 | 1,947 | 1,753 | 1,784 | 1,860 |
| MiB/s、2 回目 | 1,461 | 1,765 | 1,732 | 1,768 | 1,784 |
| CPU s/GiB (2 回目) | 2.13 | 2.19 | 2.51 | 2.47 | 2.47 |

スレッドを増やすと CPU だけが増えて (2.13 → 2.47 s/GiB) スループットは変わらない。

`benchmark-hdf5.md` で h5py に見たのと同じ形である。ただし h5py は 1 スレッド分で
止まるのに対し、zarr-python は 3 コア強までは使う ── 伸長は GIL を放すので
`async.concurrency = 10` の範囲で重なるが、チャンクごとの組み立て (スライス、
バッファの詰め替え) は 1 つのイベントループの中に並ぶ。

**プロセスを分けると伸びる。** これが「限界は 1 つのインタプリタの中にある」という証拠で、
ストレージでもコーデックでもマシンでもない。

| プロセス数 | 1 | 2 | 4 | 8 | 16 |
|---|---:|---:|---:|---:|---:|
| `mem.zarr` | 2,500 | 4,408 | 7,420 | 9,531 | 10,574 |
| `mem-shard.zarr` | 1,266 | 2,058 | 3,857 | 6,182 | 7,387 |
| `mem-noisy.zarr` | 2,169 | 3,930 | 5,557 | 5,541 | 5,573 |
| `mem-noisy.zarr` (2 回目) | 1,847 | 3,797 | 5,440 | 5,564 | 5,506 |
| `mem-noisy-shard.zarr` | 1,139 | 2,109 | 3,061 | 4,122 | 4,525 |

`mem-noisy.zarr` が 4 プロセスで止まるのは、1 プロセスが 3 コア強使うので
**4 プロセスで 16 コアを使い切る**ためである。圧縮がよく効く `mem.zarr` は
1 チャンクあたりの伸長が軽く、1 プロセスの使うコアが少ないので、16 プロセスまで
伸び続ける。

### では AEX2 の 1 コアは何に使われているのか

16 接続のときの 472 MiB/s は、zarr-python の 481 〜 490 を**下回っている**。
何に消えているかをサーバの `perf` で見た (`perf record -a -e cpu-clock`、
`aex-data-conn` スレッドのみ、100 % = サーバの CPU)。

| | 1 接続 | 16 接続 |
|---|---:|---:|
| zstd 伸長 | 69.8 % | 60.9 % |
| `memmove` (チャンクの写し) | 9.5 % | 10.3 % |
| ページのゼロ埋めとフォールト | 5.6 % | 7.1 % |
| ソケットへの写し | 5.1 % | 4.6 % |
| その他 (裾) | 10.0 % | 17.1 % |

**伸長に使えているのは 6 〜 7 割**で、残りは写しとページの世話である。
16 接続にすると伸長の取り分が 69.8 → 60.9 % に落ち、代わりに
`_raw_spin_unlock_irqrestore` が 4.3 % 現れる ── カーネルのページアロケータの
ロックである。

### 原因はチャンクごとに 4 MiB を確保し直していること

チャンク 1 個を配るたびに `Vec` が 3 回確保される (圧縮バイトの読み込み、伸長先、
そしてキャッシュに載せる `Arc<[u8]>`)。4 MiB は glibc の mmap 閾値の上なので、
確保と解放のたびに `mmap` / `munmap` が走り、カーネルはそのページをゼロ埋めし、
16 スレッドが同じアロケータのロックに並ぶ。

glibc に mmap を使わせない設定で走らせると、これがそのまま消える。

| | 中央値 MiB/s | サーバ CPU s/GiB | 1 コアあたり MiB/s |
|---|---:|---:|---:|
| 現状 | 6,746 | 2.19 | **467** |
| `MALLOC_MMAP_MAX_=0` | 8,483 | 1.91 | **537** |

**+23 %**。交互に 5 巡したが、どの巡でも `MALLOC_MMAP_MAX_=0` が速い
(6,315〜6,747 対 7,617〜8,252)。`perf` でも
`_raw_spin_unlock_irqrestore` が 4.3 → 0.8 % に落ちる。

**つまり 1 コアあたりで zarr-python に負けているのは設計の必然ではない。**
この確保し直しを無くせば 467 → 537 MiB/s となり、zarr-python (481〜490) を
1 割ほど上回る。環境変数は**証拠であって直し方ではない** ── 直すなら、
退避したチャンクのバッファをキャッシュが持ち回って次の伸長に貸す
(ついでに `DecodeCache` が `Vec<u8>` を `Arc<[u8]>` に変換するときの
まるごと 1 回の写しも消える)。デコードキャッシュは HDF5 と共用なので、
効くのは Zarr だけではない。

残る `memmove` 約 12 % のうち半分は送信バッファへの写しで、これは
「バックエンドの内部事情を送信コードから隠す」という設計が払っている代金である
(SPEC 第 7.1 節)。

### まとめ

AEX2 の 1 要求は、接続ごとに独立した OS スレッドが `pread` → 伸長 → コピーを
共有ロック無しで回すので、**1 つの要求でマシン全体を使う**。zarr-python で同じことを
するには利用者がプロセスを 16 個立てて選択を手で割り振る必要があり、それをしても
AEX2 が 1.16 〜 1.63 倍速い ── そして AEX2 のほうだけがデータを別のマシンへ
届けている。

**1 コアあたりで見ると、現状の AEX2 は zarr-python をわずかに下回る** (467 対
481〜490)。これはアロケータの churn で説明がつき、直せば 537 になる。
「Rust だから速い」のではないことは、この数字がはっきりさせている。

## デコードキャッシュは何を持っていたのか

上の測定はすべて**チャンク 4 MiB = fetch 1 個**のストアで取っている。`mkzarr.py` が
サーバ既定の fetch に合わせてチャンクを切っているからで、利用者もそうするだろうが、
その結果 SPEC 第 7.4 節が想定した場面 ── 1 個のストレージチャンクの別々の部分を
複数の接続が欲しがる ── は**一度も起きていない**。

起きていたのはこうである。fetch 1 個 = 4 MiB = チャンク 1 個が、
`read_buffer_bytes` の 512 KiB ずつ 8 回に分けて読まれる (`reader.rs`)。
8 回とも同じ接続スレッドからで、1 回伸長して 7 回ヒットする。

`DecodeCache` に hit / miss / race の計数を足して確かめた。miss は伸長の回数なので、
転送が配ったチャンク数と比べれば、キャッシュがチャンクを読み終わるまで持って
いられたかが分かる。

### チャンク = fetch のとき、キャッシュは完璧に働く

| ストア | 接続数 | MiB/s | hits | misses | races | チャンク数 | 1 チャンクあたりの伸長 |
|---|---:|---:|---:|---:|---:|---:|---:|
| `mem-noisy.zarr` (4 MiB) | 16 | 7,363 | 7,168 | 1,024 | 0 | 1,024 | **1.00** |

引きの総数 8,192 は 4 GiB ÷ 512 KiB とちょうど一致し、ヒット率 87.5 % は
8 回に 1 回しか伸長しない**理論上の上限**である。`races` は 0 ──
2 スレッドが同じチャンクを同時に伸長する競合 (`decode_cache.rs` の `ponytail:` 注記)
は一度も起きていない。**16 枚のキャッシュに 16 接続でスラッシングしている**という
CPU からの推定は誤りだった。

つまりこの構成のキャッシュは、共有キャッシュではなく**接続ごとの伸長バッファ**として
働いている。そのためにグローバルな `Mutex` と `Arc` と 4 MiB の確保を払っている。

### チャンクが fetch より大きいと、絵が反転する

`mem-noisy-big.zarr` (64 MiB チャンク 64 個、中身は同じ、キャッシュは既定の 1 GiB)。

| 接続数 | MiB/s | hits | misses | races | 1 チャンクあたりの伸長 |
|---:|---:|---:|---:|---:|---:|
| 1 | 388 | 8,128 | 64 | 0 | **1.00** |
| 4 | 478 | 7,993 | 199 | 135 | **3.11** |
| 16 | 1,375 | 7,970 | 222 | 158 | **3.47** |

ここでは確かに接続をまたいで共有している (64 チャンクに対しヒットが 7,970)。
しかし **2 接続以上になった瞬間に競合が現れ、1 チャンクを平均 3.5 回伸長する**。
miss から理論値 64 を引いた数が races とちょうど一致するので、
余分な伸長はすべて競合であって、追い出しではない。

そして**スループットは 5.4 倍落ちる** (7,363 → 1,375)。原因は 3 つ重なっている。

1. **伸長そのものが遅い。** 64 MiB のチャンクは 1 コア **764 MiB/s** でしか伸長できない
   (4 MiB なら 1,117〜1,124)。出力が L3 に収まらず、書いた先が毎回 DRAM に落ちる。
   1 接続の 388 対 634 MiB/s という差は、ほぼこの天井の比 (764/1,117 = 0.68) で説明がつく
2. **競合で 3.5 倍の伸長**
3. **1 回の miss が 64 MiB の伸長を要求する。** 512 KiB を返すために 85 ms 待たせることになり、
   その間その接続は何も送らない (これは推測。上の 2 つと違って直接は測っていない)

fetch を既定の 4 MiB から上限の 16 MiB に上げると **1,489 → 3,249 MiB/s** になる。
1 チャンクに触る接続が減って競合が減るためで、**チャンクを切り直せない利用者への
当座の手** になる。

### これが意味すること

**SPEC 第 7.4 節の「クライアントの分割方法から独立に効率が保たれる」は、測ると成り立たない。**
効率はストレージチャンクと fetch の比に強く依存する。同じデータ・同じコーデック・
同じ格納バイト数で、チャンクの切り方だけで **5.4 倍**変わる。

- **利用者への推奨**: Zarr のチャンクは転送の fetch サイズ (既定 4 MiB) に合わせる。
  合わせられないなら fetch を上げる
- **`decode_cache.rs` の `ponytail:` 注記に、測定が答えを出した。**
  「伸長中のチャンクを待ち合わせる」のは、チャンクが fetch より大きいときには要る。
  チャンク = fetch のときは races が 0 なので、そこでは何も変わらない
- 一方、**接続ごとの 1 枚を前に置く案は採らない**。チャンク = fetch のときは効くが、
  大きいチャンクのときに接続をまたぐ共有を壊す ── 測ったからこそ避けられた

## 確保し直しを直した結果

上で見た「チャンクごとに 4 MiB を 3 回確保する」を 2 段で潰した。測定はどちらも
**同じ巡の中で 2 つのビルドを交互に**回している (同じ構成でもセッションをまたぐと
9 % 振れるので、前回の記録との比較では数 % の差は読めない)。条件は `mem-noisy.zarr`、
16 接続、64 MiB キャッシュ。値は 5 巡の中央値。

### 第 1 段 —— `Arc<[u8]>` をやめる

`Arc<[u8]>` は `Vec` のバッファを引き取れない。変換のたびに 4 MiB をもう 1 回確保して
丸ごと写していた。`Arc<Vec<u8>>` にすれば所有権が移るだけで済む。

| | MiB/s | サーバ CPU s/GiB | 1 コアあたり MiB/s |
|---|---:|---:|---:|
| 直前 | 6,524 | 2.24 | 457 |
| 第 1 段 | **7,489** | **1.96** | **522** |

**+14.8 %**。5 巡すべてで第 1 段が速い (6,175〜6,824 対 7,279〜7,927)。

### 第 2 段 —— 退去したバッファを貸し回す

退去したチャンクの `Vec` を `Arc::into_inner()` で取り戻してプールに置き、次の伸長へ貸す。
まだ誰かが読んでいれば `None` が返るので貸し出されない。バックエンドは連鎖の最後の
コーデックが貸されたバッファへ書く。

| | MiB/s | サーバ CPU s/GiB | 1 コアあたり MiB/s |
|---|---:|---:|---:|
| 第 1 段 | 7,667 | 1.94 | 528 |
| 第 2 段 | **8,655** | **1.81** | **566** |

**+12.9 %**。これも 5 巡すべてで速い。

### 合わせて

| | MiB/s | 1 コアあたり MiB/s |
|---|---:|---:|
| 直前 | 6,524 | 457 |
| 第 1 段 + 第 2 段 | **8,655** | **566** |

**スループット +32.7 %、1 コアあたり +23.9 %。** 1 コアあたりでは zarr-python
(481〜490) を下回っていたのが、**16 % 上回る**ところまで来た。

### 天井に届いたことの確かめ

`MALLOC_MMAP_MAX_=0` (glibc に大きいブロックをカーネルへ返させない) が
**もう効かない**。確保し直しそのものが無くなったので、アロケータに何を頼んでも
変わらない、ということである。

| | plain | `MALLOC_MMAP_MAX_=0` |
|---|---:|---:|
| 直前 | 6,746 | 8,483 (**+23 %**) |
| 第 1 段 | 7,768 | 8,587 (+10.5 %) |
| 第 2 段 | 8,599 | 8,506 (**差は振れの内側**) |

**キャッシュの挙動は変えていない。** 計数は第 2 段の後も
`hits=7168 misses=1024 races=0` で、1 チャンクを 1 回だけ伸長するまま。

### HDF5 にも効く

デコードキャッシュは共用なので、`mem-gzip-noisy.h5` (shuffle + gzip) も測った。
16 接続、3 巡の中央値。

| | MiB/s |
|---|---:|
| 第 1 段 | 3,675 |
| 第 2 段 | **4,215** (+14.7 %) |

第 1 段が HDF5 では効きが薄い (記録の 3,617 とほぼ変わらない) のは、あちらの連鎖の
最後が `unshuffle` で、もともと新しい `Vec` を作っていたからである。第 2 段はそれも
貸されたバッファへ書くようにするので、ここで効く。

## 再現方法

[eval-mdx2.md](eval-mdx2.md) のデータ作成 (`mkzarr.py`) を済ませ、
`aex-decode-cache-64m.toml` のサーバを立ててから、クライアントで次を回した。

```console
$ ssh aex2-eval2 "bash -lc 'cd aex2 && S=http://192.168.100.207:50391
  for r in 1 2 3 4 5; do for s in 1 2 4 8 16; do
    for f in mem.npy mem.zarr mem-shard.zarr mem-noisy.zarr mem-noisy-shard.zarr; do
      case \$f in *noisy*) p=none ;; *) p=counting-f32 ;; esac
      target/release/aexbench \$S \$f --bytes \$((4<<30)) --streams \$s \
        --reps 1 --prefault --pattern \$p --label \$f
    done; done; done'"
```

ディスクの回は、各回の前にそのストアのページをサーバ側で落とす。`find -type f` が
`.npy` の 1 個も、ストアの全チャンクも同じように並べてくれる。

```console
$ ssh 192.168.100.207 "cd aex2 && target/release/dropcache \$(find ~/disk/\$f -type f)"
```

「なぜ速いのか」の切り分けは、サーバ上で 3 つのスクリプトを回した。1 コアの
コーデック天井と呼び出しスレッド数の掃引 (`why.py`)、プロセス数の掃引
(`procs.py`)、そして AEX2 側は転送の前後で `/proc/<pid>/stat` の utime + stime を
読んだ。

```console
$ ssh aex2-eval1 'pid=$(pgrep -x aex-server)
    read -r _ _ _ _ _ _ _ _ _ _ _ _ _ u s _ < /proc/$pid/stat; echo "$u $s"'
```

サーバのプロファイルは、**負荷を掛けている最中に**取る必要がある。クライアント側の
シェルを生かしたまま負荷を背景に回し、その中から `ssh` でサーバの `perf` を起動する
(`benchmarks/mdx2/zarr-prof.sh`)。`nohup ... &` を単発の `ssh` で投げると、
接続が切れた時点で負荷が消えてサーバが暇なところを記録してしまう。
`perf record -p PID` はこの VM では通らないので `-a` を使い、PMU が無いので
`-e cpu-clock` を指定する。

```console
$ ssh aex2-eval2 'bash -l ~/zarr-prof.sh 16 mem-noisy.zarr none 60'
$ ssh aex2-eval1 "sudo perf report -i ~/p-16.data --stdio --no-children \
    --comms aex-data-conn --sort symbol"
```

2 つのビルドを交互に回すには、比較したいコミットをサーバの別ディレクトリに置いて
両方ビルドし、1 巡ごとにサーバを立て直す (`ROUNDS=5 bash ab2.sh aex2-base aex2`)。
セッションをまたいだ比較は数 % の差には使えない。

キャッシュの計数はサーバの debug ログに出る。環境変数は `RUST_LOG` ではなく
**`AEX_LOG`** である (`main.rs`)。計数は累積なので、測りたい転送の前後の差を取る。

```console
$ AEX_LOG=aex_server=debug target/release/aex-server --config benchmarks/mdx2/aex.toml
...  DEBUG aex_server::control: decode cache hits=7168 misses=1024 races=0 ...
```

`zarr-why.py` と `zarr-procs.py` は `benchmarks/mdx2/` にある。

```console
$ ssh aex2-eval1 "bash -lc 'cd aex2 &&
    .venv/bin/python benchmarks/mdx2/zarr-why.py /mnt/aexram/mem-noisy.zarr &&
    .venv/bin/python benchmarks/mdx2/zarr-procs.py /mnt/aexram/mem-noisy.zarr'"
```

zarr-python の 1 プロセスの比較はサーバ上で次を実行した。

```python
import statistics, time, zarr
for path in ["/mnt/aexram/mem.zarr", "/mnt/aexram/mem-noisy.zarr",
             "/mnt/aexram/mem-shard.zarr", "/mnt/aexram/mem-noisy-shard.zarr"]:
    z = zarr.open_array(f"{path}/array", mode="r")
    runs = []
    for _ in range(5):
        t = time.perf_counter()
        out = z[:]
        runs.append(4096.0 / (time.perf_counter() - t))
        del out
    print(path, statistics.median(runs))
```
