# VM 間 (実ネットワーク) での転送性能

これまでの測定はすべて同一ホストのループバックだった。OpenStack ベースの仮想基盤
(mdx2) に VM を 2 台立て、**本物のネットワークを挟んだシングルストリーム**を測った
記録である。測定日 2026-09-17。

**結論を先に書くと、4 つある。**

1. **小口読みが 41 ms 止まる。** 制御プレーンに `TCP_NODELAY` が入っておらず、Nagle と
   遅延 ACK が噛み合う。応答が MSS を下回る帯 (256〜1344 B) で **p50 41 ms**。1 行
   直せば **107 µs — 383 倍**になる。**最優先で直すべきである**
2. **チャンクサイズが支配的になる。** 256 KiB で 745 MiB/s、16 MiB で 2,320 MiB/s と
   **3.1 倍**開く。RTT 0.7 ms が効くためで、ループバックでは見えなかった
3. **ダブルバッファリングが効かない** (メモリ常駐で ±0〜−18 %)。Linux ベアメタルの
   +57 % と正反対である。**律速がサーバの外へ出た**ので、サーバ内で仕事を割っても
   得るものがない
4. **律速は接続 1 本あたりの TCP 送信経路**である。サーバの 2 スレッドは各 35 % しか
   使っておらず、クライアントを 4 本同時に走らせると各 2,400〜2,800 MiB/s のまま
   **合計 89 Gbit/s** 出る。線もマシンも余っている

## 測定環境

VM 2 台、`aex2-eval-1` がサーバ (送信)、`aex2-eval-2` がクライアント (受信)。

| 項目 | VM (mdx2) | 比較: Linux 機 (5900X) |
|---|---|---|
| CPU | Intel Xeon (Sapphire Rapids)、16 vCPU、SMT 無効 | AMD Ryzen 9 5900X (12 コア) |
| ハイパーバイザ | KVM | — |
| L3 | **ゲストからは 16 MiB × 1、NUMA も 1** | 32 MiB × 2 (CCD が 2 つ) |
| メモリ | 31 GiB | 62 GiB DDR4-2133 |
| OS | Ubuntu 24.04.4 (kernel 6.8.0-136) | Ubuntu 22.04.5 (kernel 6.8.0) |
| NIC | `virtio_net`、**MTU 1442**、16 キュー、GRO 有効 | (ループバックのみ) |
| ストレージ | virtio ブロック (`/`) | WD Black SN750 NVMe |
| メモリ常駐 | tmpfs (`/mnt/aexram`) | tmpfs (`/dev/shm`) |
| Rust | 1.98.1、`--release` | 同じ |
| iPerf3 | 3.16 | 3.17.1 |

VM 間の RTT は **min 0.374 / avg 0.697 / max 4.101 ms**。MTU が 1442 なのは OpenStack の
トンネル (VXLAN/GENEVE) 分が引かれるためで、**MSS は 1390 B** になる。この数字が
あとで効いてくる。

テストは VM でも全通過する (199 件)。

`/dev/shm` は使えない。systemd が **ログアウト時に中身を消す**ので、測定の合間に
フィクスチャが消える。専用の tmpfs を `/mnt/aexram` に張った。

## 基準値 — 何が一番遅いか

| | VM 間 | VM 内ループバック | 比較: ベアメタル Linux |
|---|---:|---:|---:|
| `memcpy` 1 スレッド | — | 10,304 MiB/s | 11,990 MiB/s |
| `memcpy` 8 スレッド | — | 55,040 MiB/s | 13,719 MiB/s |
| iPerf3 1 ストリーム | **3,221 MiB/s** | 5,710 MiB/s | 5,188 MiB/s |
| iPerf3 1 ストリーム (`-Z`) | 3,719 MiB/s | 7,810 MiB/s | 5,863 MiB/s |
| iPerf3 4 ストリーム | 11,902 MiB/s | — | 16,137 MiB/s |
| iPerf3 8 ストリーム | 16,462 MiB/s | — | — |
| `pread` tmpfs (1 MiB) | 6,575 MiB/s | 同じ | 11,583 MiB/s |
| `pread` virtio ディスク、コールド | 1,611 MiB/s | 同じ | 2,870 MiB/s |
| `pread` virtio ディスク、ウォーム | 6,924 MiB/s | 同じ | — |

**ワイヤの 3,221 MiB/s がすべての中で最も遅い。** tmpfs の読みはその 2 倍、メモリコピー
は 3 倍ある。実運用の比率としてはこれが正しい形である。

Sapphire Rapids のメモリは 8 スレッドで 55 GB/s 出る。**メモリ帯域は 5900X の 4 倍あり、
この測定では一度も問題にならない。**

### 送信側ではなく受信側が高い

VM 間の iPerf3 が CPU をどう使うかが、ループバックとまるで違う。

| | 送信側 CPU | 受信側 CPU |
|---|---:|---:|
| VM 間、1 ストリーム | **27.4 %** | **91.8 %** |
| VM 間、1 ストリーム (`-Z`) | 17.0 % | 69.0 % |
| VM 内ループバック、1 ストリーム | 100.5 % | 85.0 % |

ベアメタルのループバックでは送信側が 1 コアを使い切っていた。**VM の実ネットワークでは
送信側が 27 % で済み、受信側が 92 % かかる。** 送信は TSO でまとめて NIC に渡せるが、
受信は MTU 1442 の小さなパケットを 1 つずつ処理するためである。

## AEX2 の結果

4 GiB を 1 転送、n = 9 (コールドディスクのみ n = 3)。出荷時の設定 (`read_buffers = 3`)、
sysctl も既定のまま。

| チャンク | tmpfs | 合成バックエンド | virtio ディスク、コールド |
|---:|---:|---:|---:|
| 256 KiB | 745 MiB/s | — | — |
| 1 MiB | 1,393 | — | — |
| 4 MiB | 2,200 | 2,077 | — |
| **16 MiB** | **2,320** | 2,228 | 1,132 |

**16 MiB で 2,320 MiB/s (19.5 Gbit/s)。** iPerf3 の 1 ストリーム 3,221 MiB/s に対して
**72 %** である。

### チャンクサイズが 3 倍を持っていく

ループバックでは 256 KiB と 16 MiB の差は小さかった。**実ネットワークでは 3.1 倍開く。**

RTT が 0.7 ms あるので、チャンク 1 つごとの往復が効く。256 KiB を 0.7 ms ごとに 1 つ
取れば 366 MiB/s が上限で、実測 745 はパイプライン分だけそれを上回っている。
**credit パイプライン (SPEC §6.6) が実ネットワークで初めて意味を持つ**ことが、この列に
出ている。

### ダブルバッファリングが効かない

`read_buffers` を 1 (逐次) と 3 (重ねる) で比べる。

| | 逐次 | 重ねる | 効果 |
|---|---:|---:|---:|
| tmpfs、16 MiB | 2,438 MiB/s | 2,320 | **−5 %** |
| tmpfs、4 MiB | 2,083 | 2,200 | +6 % |
| 合成バックエンド、16 MiB | 2,704 | 2,228 | **−18 %** |
| virtio ディスク コールド、16 MiB | 1,052 | 1,132 | +8 % |

**メモリ常駐では効かない。誤差の範囲か、むしろ負ける。** ベアメタル Linux の +57 %、
macOS の +51 % とは正反対である。

理由は CPU の置き場所である。ベアメタルでは送りスレッドが 1 コアを使い切っていたので、
読みを別スレッドに追い出せばその分が丸ごと空いた。**VM ではサーバがそもそも詰まって
いない。**

転送中のスレッド別 CPU は、

| スレッド | CPU |
|---|---:|
| サーバ `aex-data-conn` (送り) | 35.6 % |
| サーバ `aex-data-read` (読み) | 33.9 % |
| クライアント (受け) | 95.8 % |

サーバの 2 本はどちらも 3 分の 1 しか使っていない。**空いている CPU を 2 つに割っても
速くはならず、バッファの受け渡しの分だけ損をする。** 合成バックエンドの −18 % は、
読む仕事が最も軽い場合に受け渡しの費用だけが残ることを示している。

**コールドディスクでは +8 % 残る。** ディスク (1,611 MiB/s) がワイヤ (2,320) より遅い
唯一の場合で、重ねる意味があるのはここだけである。

### 律速は接続 1 本にある

クライアントを同時に増やしても、1 本あたりの速度が落ちない。

| 同時クライアント数 | 各クライアントの速度 | 合計 |
|---:|---|---:|
| 1 | 2,455 MiB/s | 2,455 MiB/s |
| 2 | 2,799 / 2,390 | 5,189 |
| **4** | 2,802 / 2,764 / 2,647 / 2,385 | **10,598 MiB/s (88.9 Gbit/s)** |

**4 本でも 1 本あたりの速度は変わらない。** 線にも CPU にもまだ 4 倍以上の余地があり、
**遅いのは「1 本の TCP 接続」という単位そのもの**である。iPerf3 が 1 → 8 ストリームで
3,221 → 16,462 MiB/s になるのと同じ話である。

### クライアントの費用はすべてカーネルにある

クライアント 1 回 20 GiB の内訳は、

```
User time (seconds): 0.03
System time (seconds): 6.55
Voluntary context switches: 40685
```

**ユーザ空間は何もしていない。** 40,685 回の自発的コンテキストスイッチは
20 GiB ÷ 512 KiB とちょうど合う — フレーム 1 つごとに `read` でブロックしている。

フレームを大きくしても改善しない。

| `read_buffer_bytes` | スループット |
|---:|---:|
| 512 KiB (既定) | 2,381 MiB/s |
| 1 MiB | 2,412 |
| 4 MiB | 2,138 |

**システムコールの回数ではなく、パケット 1 つあたりの処理が費用**だからである。
MTU 1442 では 2,320 MiB/s を運ぶのに毎秒 170 万パケットを処理することになる。

## 送信バッファの既定値が 25〜31 % 削っている

転送中のサーバ側 TCP を覗くと、

```
rtt:0.94/0.659 cwnd:3023 sndbuf_limited:1275ms(24.9%)
rtt:0.94/0.644 cwnd:3023 sndbuf_limited:2251ms(29.1%)
rtt:1.08/0.289 cwnd:3023 sndbuf_limited:3183ms(31.0%)
```

**送信側は時間の 4 分の 1 から 3 分の 1 を、送信バッファが空くのを待って過ごしている。**
`cwnd` 3023 × MSS 1390 B ≈ 4.2 MB は `net.ipv4.tcp_wmem` の上限 4 MiB そのもので、
輻輳ウィンドウがバッファに頭を押さえられている。

上限を 64 MiB に上げると、

| | 既定 (4 MiB) | 64 MiB | 効果 |
|---|---:|---:|---:|
| iPerf3 1 ストリーム | 3,221 MiB/s | 3,821 | **+19 %** |
| AEX2、tmpfs、16 MiB | 2,320 | 2,578 | **+11 %** |

`sndbuf_limited` は消え、代わりに `notsent` が 1.5〜2.9 MB 積む — 送るべきデータは
手元にあり、バッファではなく送信経路そのものが限界という形に変わる。

**AEX2 の設定にはすでに `tcp.sndbuf` がある。** 読み込まれて検証もされるが、まだ
適用されておらず、データプレーンが「適用していない」と警告を出すだけである
(`dataplane.rs`)。**これを実装すれば、システム全体の sysctl を触らずに 11 % 取れる。**

## 小口読みが 41 ms 止まる

`latbench` を VM 間で走らせると、特定の大きさだけ **p50 が 41 ms** になる。

| 選択サイズ | p50 | p99 | |
|---:|---:|---:|---|
| `GetItem` (メタデータのみ) | 91.7 µs | 128.0 µs | |
| 4 B | 94.2 µs | 109.3 µs | |
| 64 B | 95.0 µs | 108.3 µs | |
| **256 B** | **41,004 µs** | 41,671 µs | ← |
| **1,024 B** | **41,021 µs** | 41,777 µs | ← |
| **1,344 B** | **41,002 µs** | 41,730 µs | ← |
| 1,408 B | 140.5 µs | 210.0 µs | |
| 16 KiB | 159.8 µs | 201.6 µs | |
| 64 KiB | 209.0 µs | 240.2 µs | |
| 64 KiB + 4 B | 301.8 µs | 394.9 µs | データプレーン、2 往復 |
| 1 MiB | 913.8 µs | 1,034.0 µs | データプレーン、2 往復 |

**500 回中の中央値が 41 ms である。**たまに遅いのではなく、ほぼ毎回そうなる。

41 ms という数字と、帯の上端が **1,344 B と 1,408 B の間 — MSS の 1,390 B ちょうど**に
あることが答えを指している。**Nagle アルゴリズムと 40 ms の遅延 ACK タイマーの噛み合い**
である。応答が MSS に届かないと Nagle が最後の断片を握り、相手の ACK を待つ。相手は
遅延 ACK で 40 ms 待つ。MSS を超えた応答は即座に出るので、1,408 B からは正常に戻る。

原因は制御プレーンにある。`Server::serve_with_incoming_shutdown` に自前の
`TcpListenerStream` を渡しているため、**tonic の TCP 設定が適用されず、受け付けた接続に
`TCP_NODELAY` が入らない。** データプレーンは `dataplane.rs` で明示的に設定しているので
無事である。

受け付けた接続に `set_nodelay(true)` を入れて測り直すと、

| 選択サイズ | 修正前 | 修正後 |
|---:|---:|---:|
| 256〜1,344 B | 41,002〜41,021 µs | **107 µs** |
| 16 KiB | 159.8 µs | 125.1 µs |
| 64 KiB | 209.0 µs | 192.9 µs |

**383 倍である。** 修正は 1 箇所で、データプレーンにも転送性能にも影響しない。

インライン応答の上限は 64 KiB なので、**64 KiB までの読みはすべてこの帯を通りうる**。
対話的な小口読みを一往復で返すという SPEC の狙いが、いまはその帯で完全に潰れている。

同じことは VM 内ループバックでも起きる (1 KiB / 16 KiB / 64 KiB で 41 ms)。
**ループバックでも再現するので、これまでの測定で見えていてもおかしくなかった** —
`latbench` の既定サイズが帯を跨いでいたのに、誰も 41 ms を異常だと読まなかった。

## ゲストからはホストの構造が見えない

ベアメタル Linux で見つかった最大の問題は、読みスレッドと送りスレッドが別の L3 に
乗ると 36 % 落ちることだった。**VM ではこれが手当てできない。**

```
$ cat /sys/devices/system/cpu/cpu0/cache/index3/shared_cpu_list
0-15
$ lscpu | grep -E "L3|NUMA node\("
L3 cache:      16 MiB (1 instance)
NUMA node(s):  1
```

ゲストからは **L3 が 1 つ、NUMA ノードも 1 つ**に見える。ホストで実際にどう割り
当てられているかは分からず、`sched_setaffinity` で同じ L3 に寄せようにも寄せる先が
ない。逆に言えば、**VM では配置の最適化に投資しても取り返せない**。

## ベアメタルとの対比

| | ベアメタル Linux (5900X) | VM 間 (mdx2) |
|---|---:|---:|
| 経路 | ループバック | 実ネットワーク (virtio、MTU 1442、RTT 0.7 ms) |
| メモリ常駐、逐次 | 4,268 MiB/s | 2,438 MiB/s |
| メモリ常駐、ダブルバッファリング | 6,694 MiB/s | 2,320 MiB/s |
| ダブルバッファリングの効果 | **+57 %** | **−5 %** |
| チャンク 256 KiB → 16 MiB | 小さい | **3.1 倍** |
| 律速 | サーバの送りスレッド (CPU) | 接続 1 本の TCP 送信経路 |
| サーバ CPU の余裕 | 無し (1 コア飽和) | **有り (各スレッド 35 %)** |
| 効く手当て | スレッドを同じ L3 へ | **複数ストリーム、送信バッファ、パイプライン** |

同じコードが、置かれた場所で正反対の性格を見せる。**ループバックで最適化していた
ものは、実ネットワークでは効かない。**

## M4 に向けて

VM での測定から、優先順位はこうなる。

1. **制御プレーンに `TCP_NODELAY` を入れる。** 1 行で 383 倍。小口読みが本来の設計
   どおり動くようになる。**バグに近い**
2. **複数ストリーム。** 1 本が 2,320 MiB/s で頭打ちなのに、4 本並べれば
   10,598 MiB/s 出る。**実ネットワークで最も大きい伸びしろがここにある**
3. **`tcp.sndbuf` を実装する。** 設定項目はすでにあり、適用するだけで 11 %
4. **credit パイプライン。** チャンク 256 KiB と 16 MiB の 3.1 倍は往復の費用であり、
   パイプラインで埋まる分である。**ループバックでは見えなかった**
5. **ダブルバッファリングは残す。** VM のメモリ常駐では損だが、コールドディスクでは
   +8 % で、ベアメタルでは +57 % である。**切るのではなく、ストレージがワイヤより
   遅いときだけ効くと理解しておく**

L3 への固定は、VM では効かないので優先度が下がる。ベアメタルで動かす場合にのみ効く。

## 再現方法

VM 2 台に Rust 1.98.1、`protobuf-compiler`、`iperf3` を入れる (Ubuntu 24.04 の
`protobuf-compiler` 3.21 で足りる)。

```console
# サーバ側 (aex2-eval-1)
$ sudo mount -t tmpfs -o size=12G tmpfs /mnt/aexram   # /dev/shm は消されるので使わない
$ cargo build --release
$ target/release/mknpy /mnt/aexram/mem.npy 1073741824
$ target/release/aex-server --config aex.toml         # control 0.0.0.0:50191

# クライアント側 (aex2-eval-2)
$ target/release/aexbench http://192.168.100.207:50191 mem.npy \
      --bytes $((4<<30)) --chunk $((16<<20)) --reps 9
$ target/release/latbench http://192.168.100.207:50191 mem.npy --reps 200

# 律速の確かめ方
$ ss -tin dst <client>              # sndbuf_limited / rwnd_limited / cwnd
$ ps -L -o tid,comm,pcpu -p <pid>   # スレッドごとの CPU
```

`data_advertise_host` を空にしておけば、サーバは制御プレーンに届いたアドレスを
そのままデータプレーンとして知らせるので、`0.0.0.0` に束ねたままで動く。
