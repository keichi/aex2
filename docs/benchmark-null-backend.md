# ストレージを外したときの転送性能 (localhost)

読み出しをまったく行わない合成バックエンドを作り、転送経路だけの性能を測った記録で
ある。測定日 2026-09-16、環境は [M2 の測定](benchmark-m2-local.md#測定環境) と同一。

これまでの測定には常にストレージが経路に入っていた。ファイル、ページキャッシュ、
`pread`。それを外すと何が残るかを見る。

## 要約

4 GiB を 1 転送、チャンク 16 MiB。`.npy` と合成バックエンドは、セッション間の
ドリフトを排すため**同一サーバで交互に** 4 往復して対にした。

| | スループット | iPerf3 比 |
|---|---:|---:|
| iPerf3 (ループバック、`-l 1M`) | 19,501 MiB/s | — |
| iPerf3 (`-l 256K`) | 18,520 MiB/s | 95 % |
| `pread` 単体 (RAM ディスク) | 20,477 MiB/s | — |
| **AEX2、合成バックエンド** | **15,791 MiB/s** | **81 %** |
| AEX2、`.npy` (RAM ディスク) | 13,339 MiB/s | 68 % |

**ストレージを外すと 13,339 → 15,791 MiB/s (+18 %) になり、iPerf3 の 81 % に達する。**

つまり、

- **プロトコルそのものの費用は小さい。** フレーミング、多重化、チケット検証、
  ソケットの往復をすべて含めて、1 個のバッファを流して捨てるだけの iPerf3 との差は
  19 %
- **`.npy` と合成バックエンドの差 18 % が、データを読むという行為そのものの費用**
  である。その中身は次節で分解する

> **訂正**: この差は当初 38 % と記録していたが、2 つを別セッションで測ったための
> ドリフトが混ざっていた。交互に測り直した 18 % が正しい。

## 「データを読む」費用とは何か

合成バックエンドのパターン長を変えると、**読みがキャッシュから来るか、メモリから
来るか**を切り替えられる。転送されるバイト列は同一で、読み元だけが変わる。

| パターン長 | スループット |
|---:|---:|
| 64 KiB (L2 に載る) | 16,325 MiB/s |
| 1 MiB | 17,222 MiB/s |
| 16 MiB | 16,475 MiB/s |
| 2 GiB (キャッシュに載りようがない) | 16,375 MiB/s |

**変わらない。** 2 GiB のパターンからの読みは必ずメモリを一往復するが、64 KiB の
場合と同じ速度が出る。したがって **「読む費用」はメモリ帯域ではない**。

残る候補は読みのカーネル経路である。読み段だけを単体で測ると、

| 読み方 | スループット |
|---|---:|
| `memcpy` (2 GiB のバッファから) | 約 47,000 MiB/s |
| `pread` (ページキャッシュから) | 20,477 MiB/s |

**同じバイト数を運ぶのに `pread` は `memcpy` の 2.3 倍かかる。** システムコールの
出入り、ページキャッシュの探索、`copyout` の分である。読みスレッドはこの速度でしか
バッファを埋められないので、送り段と並んで律速側に回る。それが端から端までの 18 % に
なる。

言い換えると、**「データを読む費用」= カーネルを通してバイトを取り出す費用**であり、
メモリからバイトを引く費用ではない。この区別は次の問いに直結する。

## 合成バックエンドとは何か

`aex-core` の `null` バックエンド。ストレージを持たず、64 KiB の繰り返しパターンから
読みに答える。パターンは `pattern[i] == i as u8` なので、**論理バイト列の位置 p に
ある値は `p as u8`** である。受け取った側は元データを持たずに全バイトを検証できる。

64 KiB はキャッシュに載る大きさで、これは iPerf3 が同じ 1 MiB のバッファを使い回すのと
同じ性質である。つまり「読み」は残っているが、その費用はキャッシュからのコピー分
だけになる。

どこにも保存されていないデータを配るので、**明示的に有効化しない限りサーバは提供
しない**。

```console
$ aex-server --root /data --enable-null-backend
```

```rust
// <dtype>:<dim>[x<dim>...]
let handle = client.open_as("uint8:4294967296", "null")?;
let handle = client.open_as("float32:1000x200", "null")?;
```

## 結果

### チャンクサイズ掃引 (4 GiB を 1 転送)

| チャンク | `.npy` (RAM ディスク) | 合成バックエンド |
|---:|---:|---:|
| 2 MiB | 9,186 MiB/s | 13,101 MiB/s |
| 4 MiB | 9,713 MiB/s | 14,519 MiB/s |
| 8 MiB | 11,442 MiB/s | 15,621 MiB/s |
| 16 MiB | 11,805 MiB/s | 16,290 MiB/s |

合成バックエンドでもチャンクが大きいほど速い。フェッチをまたいで重ねられない
(credit 未実装) ぶんが残っているためで、ストレージとは無関係の性質である。

この表は 1 本の掃引なので 2 列の差 (+38 %) には両者のドリフトが混ざっている。
列内の傾きを見るための表であり、差は上の交互測定 (+18 %) を取ること。

### ダブルバッファリングの効きかたは「読みの重さ」で決まる

| バックエンド | 読みの重さ (送りとの比) | ダブルバッファリングの効果 |
|---|---|---:|
| 合成 (キャッシュからのコピー) | 送りより速い | **+6 %** |
| `.npy` on RAM ディスク | 送りと同程度 | **+51 %** |
| `.npy` on コールド SSD | 送りより 6 倍遅い | +3 % (誤差の範囲) |

合成バックエンドでは 15,122 → 15,994 MiB/s (チャンク 16 MiB) にしかならない。

重なりの理屈からすれば当然で、効果の上限は `1 + min(読み, 送り) / max(読み, 送り)` で
ある。**読みと送りが同じ速さのときに最大 (2 倍) になり、どちらかに偏ると 1 に近づく。**
[ダブルバッファリングの測定](benchmark-double-buffering.md) で
「ループバックではディスク上のデータに効かない」と書いたのは、この曲線の右端にいる
からであり、合成バックエンドは左端にいる。

### CPU

| | GiB あたり CPU |
|---|---:|
| サーバ (合成、逐次) | 0.066 s/GiB |
| サーバ (合成、ダブルバッファリング) | 0.075 s/GiB |
| サーバ (`.npy` on RAM ディスク) | 0.138 s/GiB |
| クライアント | 0.07 s/GiB |

**`pread` を外すとサーバの CPU がちょうど半分になる。** 読みと送りがサーバ側で
等分に効いていることの裏づけであり、ダブルバッファリングが `.npy` で 51 % 効いた
理由でもある。

## 残りの 19 % は何か

iPerf3 との差である。合成バックエンドでもまだ、

1. 64 KiB のパターンからサーバの読みバッファへのコピー (キャッシュ内)
2. 読みバッファからソケットへのコピー — iPerf3 もこれをする
3. ソケットからクライアントの配列へのコピー — iPerf3 もこれをする

に加えて、フレームヘッダの読み書き、512 KiB ごとのスレッド受け渡し、フェッチごとの
往復がある。iPerf3 は 1 MiB のバッファを何も考えずに流し続けるだけで、宛先すら持た
ない (受信側は捨てる)。**この条件差を考えると 81 % は上限に近い。**

これ以上を求めるならコピーを減らすしかない。`sendfile` がそれに当たるが、
測ってみると現状の実装より**遅い**。[sendfile を採らない理由](sendfile.md) を参照の
こと。

## この測定で分かっていないこと

- **実ネットワークでの意味。** ループバックの「ネットワーク」はメモリバスである。
  10 GbE (1,192 MiB/s) ではリンクが律速するので、ここで見えている差はすべて消える
- **合成バックエンドの「読み」をさらに削った場合。** バッファに何も書かずに送れば
  コピーが 1 回減るが、前の転送の中身がそのまま流れることになる。セッションを
  またいだ情報漏洩になるため実装していない

## 再現方法

```console
$ cargo build --release -p aex-server -p aex-bench
$ target/release/aex-server --root /tmp --enable-null-backend &
$ target/release/aexbench http://127.0.0.1:50051 uint8:4294967296 \
      --format null --itemsize 1 --pattern bytes \
      --bytes 4294967296 --chunk 16777216 --reps 6
```

`--pattern bytes` は届いた全バイトが `p as u8` であることを (計測の外で) 検査する。
速いが中身が違う、という結果が記録に残らないようにするためである。
