# 先読み (`posix_fadvise(WILLNEED)`) は現状の最速に勝てるか

[io_uring の測定](benchmark-uring.md) の副産物として、「接続スレッド自身が読むまま、
次の piece だけカーネルに先読みさせる」方式 (`poolbench` の `fadvise`) が io_uring と
同じ効果を出すことが分かった。ここでは**いまのサーバが出せる最速**と正面から比べ、
あわせて**読みスレッド (`read_buffers ≥ 2`) がまだ要るか**を判定する。測定日 2026-09-20。

## 結論

1. **ディスクでは先読みが大きく勝つ。** 連続で 2,521 → 2,724 MiB/s (+8 %)、4 接続どうしなら
   1,753 → 2,710 (+55 %)。非連続は桁違いで、**1 接続 119 → 885 (7.4 倍)**
2. **読みスレッドは削除してよい。** `read_buffers ≥ 2` が唯一まだ勝っていたのは
   「1 接続・コールド・連続」だが (先読み 1,498 に対し 1,935)、**同じスレッド 2 本を
   接続 2 本に使えば先読みだけで 2,514 出る**。スレッド数を揃えるとどの点でも
   先読みが同等以上になる
3. **先読みは接続数を要らなくする。** ディスク非連続は **1 接続で飽和**し (885 / 898 /
   887 / 923 / 903)、連続も 2 接続で上限の 93 % に達する。いまは 16 接続でも届かない
4. **メモリ常駐では 0〜13 % 負ける。** ページが既にあるので advise は syscall が増えるだけ。
   「ディスクが最優先、メモリ間は二の次」という優先順位のもとでは許容できる

## 条件

- サーバ `aex2-eval-1`、クライアント `aex2-eval-2`。構成は [eval-mdx2.md](eval-mdx2.md)
  (16 vCPU / 31 GiB、kernel 6.8.0-136、virtio NIC、RTT 0.7 ms、MTU 1442)
- `REVISION`: `f7c9c34`。Rust 1.98.1。sysctl は既定のまま、netem なし
- iPerf3 (server → client、`-R`、1 本 / 16 本): 直前 26.6 / 135、直後 26.1 / 146 Gbit/s
- 1 点あたりファイル上 4 GiB を 1 回、全条件を 1 巡する組を 5 周。表は中央値、単位は MiB/s
- **2 接続の列だけは同じ revision の別の回**で測った (掃引の後に追加したため)。
  他の列と直接比べるときはこの点に注意する
- ディスクは各回の前に `posix_fadvise(DONTNEED)`。ホスト側のキャッシュは落とせないので、
  「コールド」はゲストから見たコールドである

## 何を比べたか

| 方式 | スレッド / 接続 | バッファ | 相当 |
|---|---:|---:|---|
| `serial` | 1 | 1 | いまの既定 (`read_buffers = 1`) |
| `pair` | 2 | 3 | いまの `read_buffers = 3` |
| `fadvise` | **1** | **1** | 提案。次の 8 piece を `WILLNEED` で先読み |
| `pair-fadvise` | 2 | 3 | 両方。読みスレッドが先読みもする |

非連続は「16 KiB の断片を 64 KiB おき」(密度 1/4)。`selection.rs` が近接断片を span に
まとめた**あとに**残る読みの姿で、隙間が `SPAN_GAP_BYTES` より広いのでまとめられない。
値は sink に届いたペイロードで、ファイル上はその 4 倍を走査している。

## 読みスレッドは、スレッド数を揃えるとどこでも負ける

ディスク・連続を「使ったスレッド数」で並べ直す。接続 1 本につき `serial` / `fadvise` は
1 スレッド、`pair` / `pair-fadvise` は 2 スレッド。

| スレッド | 先読みのみ | 読みスレッド併用 | 読みスレッドのみ |
|---:|---|---|---|
| 1 | **1,498** (1 接続) | — | — |
| 2 | **2,514** (2 接続) | 1,935 (1 接続) | 1,225 (1 接続) |
| 4 | **2,710** (4 接続) | 2,530 (2 接続) | — |
| 8 | **2,724** (8 接続) | 2,648 (4 接続) | 1,805 (4 接続) |
| 16 | 2,644 (16 接続) | **2,693** (8 接続) | 2,285 (8 接続) |

**読みスレッドが唯一勝っていた「1 接続」も、同じ 2 スレッドを接続 2 本に使えば逆転する**
(1,935 → 2,514)。クライアントは接続数を自分で決められるので、1 接続に縛られる状況はない。
したがって `read_buffers ≥ 2` を残す理由は残っていない。

## サーバに入れて測り直す

`poolbench` は送信経路だけを切り出したもので、FETCH の往復がない。実物のサーバに
入れて `aexbench` で測ると、**同じ仕組みでも窓の切り方ひとつで符号が変わった**。

### FETCH の境界で窓を止めると、先読みしないより遅い

サーバの reader は FETCH ごとに範囲を渡される。最初の実装は窓をその FETCH の中に
収めていた (先読みは既定 4 MiB、FETCH も既定 4 MiB)。1 接続・コールドディスクで:

| 先読みの窓 | MiB/s |
|---|---:|
| なし | 1,124 / 1,120 / 1,148 |
| 256 KiB | 470 / 476 / 444 |
| 1 MiB | 1,039 / 1,030 / 1,037 |
| **4 MiB** | **1,430 / 1,349 / 1,329** |
| 16 MiB | 1,408 / 1,466 / 1,314 |

FETCH の中で止めた版は 776〜839 で、**先読みなしより 3 割遅い**。浅い窓 (256 KiB) が
半分以下になるのが同じ現象を極端にしたもので、理由はこう考えられる:
明示的に先読みしたページには、カーネルが自分の先読みを次に進めるための印
(`PageReadahead`) が付かない。**こちらの窓がカーネルの適応先読みを置き換えてしまう**ので、
窓が浅ければ浅いなりの性能に落ちる。窓を FETCH の外へ伸ばすとカーネルより深くなり、
初めて勝つ。

### 実サーバでの効果

`aexbench`、コールドディスクの `.npy` 4 GiB、n = 5。変更前後のバイナリを同じループで
交互に走らせ、各回の前に `dropcache` した。

| 接続 | 変更前 | 変更後 | 差 |
|---:|---:|---:|---:|
| 1 | 1,081 | **1,296** | +20 % |
| 4 | 1,699 | **2,143** | +26 % |
| 8 | 2,217 | 2,236 | +1 % |

メモリ常駐 (tmpfs) は 1 接続 1,794 → 1,856、8 接続 8,785 → 8,645 で、どちらも測定の
揺れの内側だった。`poolbench` で見えた tmpfs の損 (最大 −13 %) は、実物では
1 piece あたりの仕事が多いぶん埋もれる。

8 接続で差がないのは、そこが既に装置の上限だからである。**先読みの値打ちは
「同じ速度をより少ない接続で出せること」**にある。

## 測っていないこと

- **メモリ常駐と分かっているときに advise を止める規則。** `preadv2(RWF_NOWAIT)` は
  ページキャッシュに無いとき `EAGAIN` を返すので、「外したときだけ先読みする」形にすれば
  tmpfs の損を消せる可能性がある。10 行程度で試せるが未測定
- **1 KiB 未満の断片。** advise が syscall を倍にするだけで逆効果になることが
  [io_uring の測定](benchmark-uring.md) で分かっている。実装するなら小さい span には
  advise しない
- **FETCH をまたいだ先読み。** `poolbench` に FETCH の往復がないので測れていない
- **macOS。** `posix_fadvise` は無い (`F_RDADVISE` が相当)。サーバとしては使わない方針
- **ベアメタルと NVMe、ネットワーク FS**

## 再現方法

`poolbench` と掃引スクリプトは削除した。再現するときはコミット `7ff1f07` を checkout する。

```console
$ benchmarks/mdx2/sync.sh
$ benchmarks/mdx2/fadvise-sweep.sh 5  | tee ~/fadvise.txt
$ benchmarks/mdx2/one-conn-sweep.sh 7 | tee ~/one-conn.txt   # 1 接続を深く
$ ssh aex2-eval2 'cat ~/logs/fadvise-sink.log'    # 受信側の CPU。送信側と同じ順
```
